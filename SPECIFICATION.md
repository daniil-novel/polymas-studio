# 01. Продуктовая спецификация PolyMAS Studio

Версия 0.1.0 · 2026-09-08 · Предлагаемая исходная спецификация.

## 1. Назначение

PolyMAS Studio — настольный редактор, в котором пользователь проектирует, запускает и наблюдает системы ролевых ИИ-агентов. Агент может работать самостоятельно, взаимодействовать с другими агентами, обращаться к разрешённым источникам знаний и входить в холон. Холон может включать другие холоны.

Первый исполнитель — установленный Codex CLI. В дальнейшем добавляются Claude Code CLI и API-провайдеры через одинаковый контракт адаптера. Доступность функций каждого провайдера показывается явно. Интерфейс не обещает одинаковые возможности у разных исполнителей.

Исходная метафора — рабочая область знаний, знакомая по Obsidian, с живым графом экземпляров агентов. Результат работы системы — проверяемые сообщения, решения и артефакты. Граф объясняет, кто что делает и от кого зависит.

Слово «ROI» в исходном голосовом описании трактуется как «рой». Финансовая окупаемость не является обязательной метрикой продукта. Для эксплуатации нужны расход, время, качество результата и частота ошибок.

## 2. Предположения и границы

1. Первый целевой клиент: Windows 11 x64, русский интерфейс, настольная рабочая область. Архитектура допускает macOS/Linux и подключение удалённых исполнителей.
2. Начальная поставка: приложение одного локального пользователя. Командный сервер — последующая поставка с собственной авторизацией и разграничением доступа.
3. Данные и секреты по умолчанию остаются на машине пользователя; запросы модели уходят выбранному провайдеру, MCP-запросы — выбранным серверам.
4. «Локально» означает локальное управление процессами и файлами. Это не обещание работы облачной модели без интернета.
5. Создание спецификации не требует подключения аккаунта или запуска тысяч платных заданий. Все указанные показатели нагрузки — критерии будущей проверки.
6. Поддерживаемые версии Codex и MCP фиксируются перед каждым выпуском. Установленный при подготовке CLI: 0.144.1; проверены справки команд, реальные задачи в нём для этой спецификации не выполнялись.

## 3. Словарь и строгие инварианты

| Понятие | Определение |
|---|---|
| Рабочая область | Изолированный набор проектов, ролей, агентов, холонов, запусков, подключений и политик |
| Роль / RoleTemplate | Версионируемая инструкция, рекомендуемые инструменты, формат результата и правила работы. Сама роль не исполняется |
| Экземпляр / AgentInstance | Постоянный ID, закреплённая версия роли, собственные сессии, почтовый ящик, рабочая папка, права и состояние |
| Сессия | История диалога одного экземпляра с конкретным исполнителем. У агента могут быть последовательные сессии; активный turn не более одного |
| Процесс / RuntimeProcess | Один OS-процесс Codex для одного работающего экземпляра. После завершения turn процесс exec может закрыться |
| Попытка / Attempt | Одна попытка исполнения подзадачи; имеет свой ID, вход, результат и причину завершения |
| Холон / Holon | Группа агентов и/или вложенных холонов с внешним контрактом, границами доступа, бюджетом и правилом завершения |
| Запуск / Run | Исполнение конкретной задачи на неизменяемом снимке архитектуры и конфигурации |
| Топология | Разрешённые направления взаимодействия. Наличие ребра не означает факта общения |
| Сообщение | Явный объект с отправителем, получателями, типом, полезной нагрузкой и статусом доставки |
| Центральное ядро | Пользовательское сочетание необязательного ИИ-координатора и/или общей памяти |
| Координатор | Обычный агент с ролью маршрутизации/синтеза. Его процесс и расходы входят в общие числа |
| Общая память | Источник знаний, доступный определённым участникам; не модель и не агент |
| MCP-подключение | Настройка доступа к MCP-серверу; наличие подключения не даёт права всем агентам |
| Граф знаний | Сущности, утверждения, документы и связи с происхождением. Отдельный слой от графа агентов |
| Технический контур управления | Планировщик, журнал, политики и доставка. Работает без центрального ИИ |

**INV-01.** Два экземпляра никогда не имеют общий AgentInstance ID, записываемый mail inbox или активную сессию.

**INV-02.** В пределах одного attempt один живой процесс Codex принадлежит ровно одному агенту; уникальность обеспечивается lease и fencing token. Количество работающих агентов нельзя подменять количеством ролей или вызовов одной общей сессии.

**INV-03.** Завершение процесса не удаляет экземпляр. Повторный turn запускает новый выделенный процесс и продолжает явную сессию этого же агента.

**INV-04.** Любой запуск ссылается на зафиксированные версии роли, топологии, MCP bindings, политики, модели/адаптера и входных материалов.

**INV-05.** Ни модель, ни содержимое MCP/документа не может расширить права, бюджет или лимит экземпляров. Эти ограничения проверяет приложение вне модели.

**INV-06.** Общее число экземпляров включает координаторов. Оператор видит отдельно количество элементов графа и количество агентов: хранилища и холоны не увеличивают число процессов.

**INV-07.** Смена ядра не уничтожает историю, знания и созданные экземпляры.

**INV-08.** У каждой отображаемой активности есть источник события и время наблюдения; пропуск телеметрии не заменяется вымышленным событием.

**INV-09.** Отдельный процесс и отдельная папка сами по себе не являются границей безопасности. Приложение показывает фактический уровень изоляции.

## 4. Пользователи и основные задачи

| Пользователь | Требуемый результат |
|---|---|
| Автор системы | Создать роли, количество экземпляров, группы и допустимые связи без написания инфраструктурного кода |
| Оператор | Отправить задачу нужной части системы, видеть ход работы, вмешаться, принять результат |
| Разработчик интеграций | Добавить исполнитель или MCP-рецепт по контракту без изменения редактора |
| Администратор командной установки | Управлять исполнителями, правами, секретами, лимитами и аудитом |

Один человек может совмещать все эти роли. Интерфейс сначала показывает понятные действия; технические параметры находятся в раскрываемых настройках.

## 5. Функциональные требования

### FR-01. Рабочие области

Создать, открыть, переименовать, экспортировать и архивировать рабочую область. Шаблоны: «Один агент», «Команда с координатором», «Независимые агенты», «Несколько холонов».

Экспорт конфигурации исключает секреты и приватную историю по умолчанию. Импорт начинается с проверки схемы, совместимости исполнителей и путей. Восстановление привязок к секретам выполняется мастером.

### FR-02. Редактор ролей

Поля: название, описание, инструкция, ожидаемый результат, критерии завершения, допустимые получатели, правила эскалации, исполнитель, выбор модели, MCP, права файлов/сети, лимиты turn/времени/токенов.

Сохранение создаёт новую неизменяемую версию. Редактирование роли не меняет активные запуски. Предусмотреть diff двух версий, дублирование, откат путём новой версии и применение выбранным экземплярам со следующего запуска.

Инструкция роли не называется системным промптом провайдера, если адаптер не может установить системное сообщение. UI показывает способ применения инструкции: «передаётся во вход задачи» или «поддерживается отдельным полем исполнителя».

### FR-03. Создание экземпляров

Числовое поле задаёт любое допустимое целое N от 1; быстрые значения 1, 10, 100, 1000, 5000. Ползунок — вспомогательный, логарифмический; точное значение вводится клавиатурой.

Поля: версия роли, N, шаблон имён, холон, параметры по экземплярам, рабочая папка/режим файлов, bindings, initial session policy. Предпросмотр показывает первые экземпляры и итоговое число.

Массовая операция транзакционна на уровне определения: либо создаётся весь заданный набор, либо ни одного. Материализация папок/рантаймов — отдельный возобновляемый job с индивидуальными ошибками. Повтор команды с тем же idempotency key не создаёт дублей.

Дублирование экземпляра создаёт новый ID и новую историю по умолчанию. Копирование истории — отдельная операция fork с записью происхождения и без копирования секретов.

### FR-04. Численность и масштабирование

Два независимых поля: «Всего экземпляров N» и «Одновременно работают C». Всегда 1 ≤ C ≤ N для работающей системы; конфигурация без агентов допускается только как черновик.

Режимы:

- Фиксированное число: N стабильно.
- По очереди задач: добавить экземпляры заданной роли при устойчивом росте очереди.
- По правилам: условие → действие над желаемым числом экземпляров с жёсткими min/max.

Правило масштабирования не исполняет произвольный код. Пример: очередь роли > 20 в течение 60 секунд → +2 экземпляра, не чаще одного раза в 120 секунд, максимум 40. Уменьшение: очередь = 0 и агент idle > 10 минут → завершить свободный runtime и архивировать выбранный незанятый экземпляр, минимум 4. Сначала dry run с прогнозом изменений.

Саморепликация моделью запрещена по умолчанию. Агент может запросить расширение; policy engine ограничивает запрос теми же правилами. Встроенные subagents Codex не используются как незаметная замена отдельным экземплярам PolyMAS.

### FR-05. Холоны

Холон содержит собственную цель, участников, входной/выходной формат, приоритет, бюджет, политику общения, необязательную память и coordinatorAgentId.

Вложенность — дерево владения без циклов, до 16 уровней в первой модели. У агента один owning holon; участие в других задачах обеспечивается адресацией/связями, а не вторым владельцем.

Снаружи холон можно адресовать как единицу. Он раскладывает задачу по правилу dispatch и возвращает агрегированный результат. Это системная граница, а не дополнительный скрытый LLM. При семантическом синтезе назначается видимый агент-синтезатор.

Правила dispatch: один подходящий участник; явно перечисленные участники; все непосредственные исполнители; подзадачи по плану координатора. Рекурсивная широковещательная отправка всем потомкам требует явного выбора и показывает число адресатов.

### FR-06. Архитектуры и ядро

Предустановки:

| Режим | Координатор | Память | Маршрутизация |
|---|---|---|---|
| Один агент | Нет | Необязательна | Прямой turn одного Codex |
| Независимые | Нет | Отдельная или общая | Оператор назначает задачи; межагентные сообщения выключены |
| Сеть | Нет | Необязательна | Сообщения по разрешённым рёбрам |
| Звезда | Да | Необязательна | Координатор распределяет и собирает |
| Холоническая | На выбранных уровнях | На выбранных уровнях | Контракты групп и межгрупповые связи |
| Пользовательская | По конфигурации | По конфигурации | Редактируемый ориентированный граф |

Переключатели «ИИ-координатор» и «Общая память» независимы. Включение координатора предлагает назначить существующего агента или создать нового с явным увеличением N. Выключение удаляет привязку, но не удаляет агента.

Новая топология сохраняется как черновик; активный run продолжает старую ревизию. Отзыв доступа и аварийная остановка действуют немедленно как отдельные события политики. Опциональная миграция run допускается только между turn с просмотром затронутых задач.

### FR-07. Задачи и чат

Один composer поддерживает адресатов: отдельный агент, выбранная группа, холон, вся система. Поля задачи: формулировка, вложения/ссылки, ожидаемый результат, критерии приёмки, deadline, бюджет, приоритет, политика завершения.

Глобальная задача не рассылается автоматически каждому агенту. В режиме с координатором поступает координатору; без него — выбранному правилу dispatch. Перед запуском отображаются предполагаемые получатели и предел параллелизма.

Локальная задача привязана к выбранному ID и может выполняться независимо от соседей, если хватает ресурсов.

Чат — последовательность сообщений с контекстом выбранного адресата. Когда exec занят, новый ввод помещается в очередь следующего turn; доступна явная команда «Прервать и отправить». Вставка текста в середину исполнения обещается только адаптером с capability steer.

Задачи могут иметь зависимости DAG. Цикл зависимостей запрещён; обычная топология общения может содержать циклы и ограничивается TTL и бюджетами сообщений.

### FR-08. Правила распределения и завершения

Каждая подзадача имеет assignee, input snapshot, output contract и acceptor. Успешное завершение процесса — технический факт; приёмка результата — отдельное состояние.

Поддержать all_required, quorum, first_accepted и manual. Для quorum задаются k и число обязательных проверок; голос отсутствующего участника не считается положительным. first_accepted отменяет ненужные работы только после приёмки.

Автоматический план координатора проходит структурную проверку: существующие адресаты, корректный DAG, права, budgets, максимальное число дочерних задач. Изменение плана сохраняется новой версией.

«Задача завершена» означает, что выполнено выбранное правило приёмки, приложены результаты, нет обязательных незавершённых работ. Частично успешный запуск отмечается отдельно. Оценка «модель сказала готово» недостаточна.

### FR-09. Общение агентов

Типы: task_request, evidence, question, answer, critique, result, escalation. Каждое сообщение содержит sender, recipients, correlationId, causationId, replyTo, TTL, размер и ссылки на артефакты.

По умолчанию сообщение адресуется одному получателю или контракту холона. Broadcast ограничен fan-out, показывается в UI и расходует бюджет. Модель не отправляет сообщения через произвольные файлы или shell как обход платформенной доставки.

Доставка: accepted → queued → delivered_to_context → acknowledged либо rejected/expired/dead_letter. accepted означает запись в надёжное хранилище; delivered_to_context — успешную передачу во вход конкретного turn. acknowledged требует явного прикладного подтверждения, если оно предусмотрено контрактом.

Получатель не обязан отвечать на каждое сообщение. Инструкция и тип сообщения задают необходимость ответа. Антипетля: ограничение hops, maxReplies, duplicate body detection в пределах диалога, time budget и эскалация при отсутствии прогресса.

### FR-10. MCP

Каталог подключений содержит понятные рецепты, свои серверы, версию, издателя, способ авторизации, обязательные поля и диагностические шаги.

Каждая карточка имеет переключатель, статус здоровья и область доступа. Первое включение ненастроенного подключения открывает мастер; переключатель не становится «подключён», пока проверка не завершилась.

Отдельно задаются tools allowlist, ресурсы/папки/namespace, чтение/запись и required/optional для роли или задачи. Сбой optional MCP даёт предупреждение; сбой required блокирует запуск или зависимую подзадачу.

MCP не заменяет установку базы, загрузку документов, индексацию или выдачу прав. Эти операции показаны отдельными шагами.

### FR-11. Знания и память

Источники: разрешённые локальные каталоги, документы, подключённые БД, удалённое файловое/объектное хранилище через MCP. Источник имеет владельца, namespace, видимость, retention и политику обновления.

Конвейер: discover → fetch → parse → index → ready; для некоторых MCP доступ возможен on-demand без локального индекса. Неопознанный формат имеет состояние unsupported, а не пустой успешный индекс.

Каждое утверждение в графе знаний: текст/тип, source URI, source version/hash, автор, время, namespace, статус проверки, связи supports/contradicts/derived_from. Вывод агента хранится как утверждение с происхождением; не становится подтверждённым фактом автоматически.

Граф знаний и агентный граф разделены на уровне типов и хранения. Объединённый вид показывает связь «агент прочитал источник»/«агент создал утверждение».

Без общей памяти агент использует собственный контекст и явно разрешённые источники. Отключение памяти прекращает новые обращения; ранее переданные сведения остаются в истории. Для исключения такого контекста нужна новая сессия, UI это объясняет.

### FR-12. Наблюдаемость

Граф показывает состояние runtime, задачи, очередь, доставку сообщений и обращения к хранилищам. Выбор узла открывает роль, текущую задачу, события, диалог, результаты, права и диагностику.

Показываются доступные публичные планы/краткие сводки исполнителя, вызовы инструментов и результаты. Полный скрытый ход рассуждений не обещается и не имитируется. Если провайдер не отдаёт прогресс, UI показывает «Выполняется; подробные события недоступны».

Есть live/replay, фильтры времени и типов, причинные связи, поиск по ID/роли/имени, список агентов как доступная альтернатива графу. Replay не запускает инструменты повторно.

### FR-13. Управление работой

- Пауза выдачи: новые задания не стартуют, активные turn доходят до границы.
- Прервать агента: отменить текущий attempt; артефакты сохранить с пометкой partial.
- Остановить run: закрыть вход задач и каскадно отменить его потомков.
- Аварийная остановка workspace: запрет новых lease и сетевых/MCP операций, завершение принадлежащих приложению процессов.
- Повтор: новая попытка; автоматический повтор разрешён только при классифицированном transient failure и известной безопасности внешних эффектов.

UI показывает различие «команда остановки принята», «процесс завершён» и «внешняя операция уже могла завершиться».

### FR-14. Результаты

Артефакт: ID, тип, версия, hash, автор/attempt, время, путь/объектный URI, статус приёмки. Поддержать Markdown, текст, JSON, изображения, прикреплённые файлы и diff кода; прочие типы можно скачать.

Общий output собирается в отдельное место. Несколько агентов не пишут одновременно в один файл. Для кода — отдельные worktree/копии и этап интеграции с проверкой конфликтов.

У каждой принятой задачи есть финальное сообщение с кратким результатом, списком артефактов, ограничениями и невыполненными критериями.

### FR-15. Ресурсы и расход

Показывать созданные, queued, running, waiting, stopped, failed; CPU/RAM исполнителей; задержку очереди; throughput; ошибки; tool latency; provider usage, если есть.

API-стоимость рассчитывается только по известным usage и выбранной версии прайс-листа, с пометкой «оценка». Неизвестный расход — неизвестен, не 0. Вход через ChatGPT показывает доступные provider limits или «Лимит не предоставлен»; денежная стоимость каждого turn по подписке не выдумывается.

Один набор credentials имеет общий ограничитель. Создание новых экземпляров не обходится как создание новых квот.

### FR-16. Импорт, экспорт и история

Экспорт архитектуры человекочитаем и проходит JSON Schema. Нужны migrationVersion, schemaVersion, roleVersions и connection placeholders. Секреты исключаются; локальные абсолютные пути требуют remap при импорте.

Изменения конфигурации фиксируются с author, timestamp, reason, previousRevision. Undo/redo для черновика; изменение уже запущенной истории недопустимо.

### FR-17. Будущие исполнители

Runtime registry обнаруживает наличие Codex, Claude Code и API-конфигураций. В первом выпуске реально доступен только Codex; остальные помечаются «Запланировано» без рабочего переключателя.

Будущий API-агент сохраняет семантику отдельного экземпляра/контекста; его процессная модель будет описана в отдельной спецификации адаптера. Условие «1000 Codex = 1000 Codex CLI» не размывается последующим API-пулом.

### FR-18. Эксплуатация и доступ

Локально — OS-права, секретное хранилище, заблокированное внешнее управление по умолчанию. Командная версия — роли viewer/operator/editor/admin, разграничение workspace, отдельные identities удалённых worker.

Нужны миграции БД, резервное копирование, восстановление, экспорт диагностического пакета с редактированием секретов, подписанные обновления и откат совместимой версии.

## 6. Масштаб и ресурсы

| Масштаб | Продуктовое поведение | Условие доказанной поддержки |
|---|---|---|
| N=1, C=1 | Один узел, один Codex, прямой чат | Реальная end-to-end проверка |
| N=10, C=10 | 10 отдельных процессов и историй | Параллельный smoke + отмена + проверка изоляции |
| N=1000, C=10 | Все 1000 экземпляров существуют; 10 исполняются, остальные ждут | Надёжная очередь и UI 1000 узлов |
| N=1000, C=1000 | 1000 выделенных Codex, распределяемых по worker | Реальные разрешённые ресурсы и квоты, длительный нагрузочный прогон |
| N=5000+ | Вложенные холоны, агрегация графа, lazy history | Отдельный сертифицированный профиль масштаба |

Целевой размер редактируемой конфигурации первой модели — 5000 экземпляров и 25000 разрешённых рёбер. Это лимит продукта для первого набора нагрузочных сценариев, а не теоретический предел.

Требуемая RAM = overhead приложения + C × измеренная p95 RAM Codex + MCP overhead + индекс/кэш + резерв. До измерения конкретного runtime численные обещания памяти не даются.

Запрос C выше доступной вместимости не приводит к зависанию: admission показывает ограничения и даёт выбрать явный лимит, очередь или подключение worker. Для задания «требуются все 1000 одновременно» запуск блокируется до наличия 1000 слотов; нельзя молча запускать только 10.

Полный граф all-to-all запрещён как автоматический default: для 1000 узлов он создаёт 999000 направленных связей. Используются holon gateways, topic subscriptions с ACL и явные рёбра.

## 7. Что входит в первый production-выпуск

Локальные рабочие области, роли и версии, независимые экземпляры, ручные холоны, отсутствие/наличие координатора, optional memory, Codex exec adapter, прямые и глобальные задачи, надёжная очередь, платформенные сообщения, MCP master для файлов/Neo4j/custom, граф и список, артефакты, cancel/recovery, аудит и бюджеты.

Для запуска первая production-ступень должна доказать 1–10 одновременных Codex на определённом тестовом стенде. Создание 1000+ экземпляров в этом же выпуске возможно с очередью и честным отображением фактического C.

Полная цель продукта включает удалённых worker и 1000+ одновременно работающих Codex. Это обязательный следующий выпуск, а не замена требования пользовательским демо.

## 8. Что не обещается исходной спецификацией

Неограниченная подписочная квота; вывод скрытых рассуждений; автоматическая истинность графа знаний; exactly-once для любых внешних инструментов; произвольная безопасная установка неизвестного MCP; одинаковая семантика pause у всех CLI; автоматическая миграция сессии между провайдерами.

Каждый из этих случаев имеет конкретное поведение ошибки или ограниченной возможности, описанное в последующих документах.

## 2. UI-01. Первый запуск

Четыре шага, всегда доступна отмена без повреждения окружения:

1. **Рабочая область.** Название, папка, шаблон «Один агент / Команда / Пустая». Показ свободного места и доступа к каталогу. Существующие файлы не заменяются.
2. **Codex.** Автопоиск бинарника, версия, происхождение, кнопки «Выбрать файл», «Открыть инструкцию установки». Установка требует явного действия пользователя в приложении. После выбора проверяется подпись/хэш поставки, если доступны, и capability probe. Неизвестный бинарник не запускается автоматически.
3. **Вход.** «Через ChatGPT» и «API-ключ» как равноправные способы. Для ChatGPT — браузерный вход штатным Codex; пароль не запрашивается приложением. Для API — защищённое поле, кнопка «Сохранить в системе», скрытие после сохранения.
4. **Проверка.** Версия CLI, доступ к рабочей папке, наличие авторизации. Короткий реальный запрос к модели запускается отдельной кнопкой с указанием, что расходуется лимит. Настройку можно закончить без него со статусом «Авторизация обнаружена; запрос не проверен».

Отсутствующий CLI, неподдерживаемая версия, незавершённый OAuth, 401, отказ сети и недостаток диска отображаются отдельными причинами. Ссылка «Подробнее» открывает очищенный диагностический текст.

После мастера шаблон «Один агент» создаёт один экземпляр и открывает его чат/граф. Самопроизвольного запроса модели нет.

## 3. UI-02. Обзор

Заголовок рабочей области и кнопки «Новая задача», «Создать агента», «Настроить архитектуру».

Четыре компактных блока: агенты (созданы/работают/ожидают), текущие запуски, нерешённые запросы, здоровье подключений. Ниже — последние принятые результаты и задачи, требующие внимания.

Счётчики рассчитываются из проекций backend с timestamp. Для недоступного worker пишется «Нет связи»; последнее значение помечается устаревшим.

Пустая область показывает последовательность «Подключите Codex → создайте роль → добавьте экземпляры → задайте цель». Демо-проект можно открыть отдельно; он постоянно помечен «Демо».

## 4. UI-03. Главный граф

### 4.1. Компоновка

При окне 1600×1000: верхняя панель 54 px; левая область 220 px; правая панель 320 px; нижний журнал по умолчанию 180 px; остальное — холст. Все боковые панели можно свернуть и менять их ширину в установленных пределах.

Слева под навигацией — дерево холонов с количеством экземпляров и индикатором текущей работы. Выбранный холон подсвечивается на графе и ограничивает контекст новых задач.

Над холстом — вкладки «Агенты / Знания / Потоки», переключатель «Редактирование / Наблюдение», фильтры и «Архитектура». Внизу — fit, zoom, миникарта и легенда.

Справа — инспектор выбранного агента, холона, ребра, источника или события. Без выбора — краткие параметры системы и инструкция действия, а не пустой большой контейнер.

Нижняя панель — «Ход выполнения / Сообщения / Инструменты / Ошибки». Время, тип, отправитель, адресат, краткое действие, длительность/результат. Строка события открывает причинную цепочку.

### 4.2. Узлы и рёбра

| Элемент | Форма и смысл |
|---|---|
| Агент | Круг; подпись имя + номер, собственный ID в инспекторе |
| Выбранный агент | Двойной контур; цвет состояния сохраняется |
| Координатор | Такой же круг + маленький символ роли; входит в N |
| Холон | Область вокруг дочерних узлов; свёрнутый холон — контейнер с числом участников |
| Память/БД | Шестиугольник или цилиндр с текстом типа; не агент |
| Документ | Прямоугольник с загнутым уголком |
| Утверждение | Ромб/малый типизированный узел в режиме знаний |
| Разрешённая связь | Тонкая тусклая направленная пунктирная линия |
| Переданное сообщение | Временный световой импульс по направлению доставки |
| Вызов памяти | Фиолетовое ребро с символом чтения/записи |
| Ошибка передачи | Короткий красный штрих и значок; подробности в журнале |

Цвет роли не заменяет цвет состояния. Если пользователь назначает роли цвет, он отображается дополнительным маркером/подписью.

### 4.3. Состояния агента на графе

| Состояние | Вид | Текст |
|---|---|---|
| Новый / idle | Серый круг, без свечения | «Готов» |
| queued | Серый с символом очереди | «В очереди» |
| starting | Мятный контур, медленный обвод | «Запускается» |
| running | Мятный свет с мягкой пульсацией | «Работает» |
| tool_wait | Значок инструмента | «Ожидает инструмент» |
| waiting_message | Значок сообщения, без активного свечения | «Ожидает ответ» |
| waiting_user | Янтарный значок вопроса | «Нужно решение» |
| rate_limited | Янтарный таймер | «Ожидает лимит» |
| paused | Символ паузы | «Приостановлен между шагами» |
| stopping | Контур с квадратом | «Останавливается» |
| failed | Красный значок ошибки | «Ошибка» |
| offline/stale | Штрихованный серый контур | «Нет свежих данных» |
| completed | Статичный check; без пульсации | «Завершил задачу» |

Свечение означает наблюдаемую активность runtime, не загрузку процессора и не содержание мыслей. После потери heartbeat активный эффект прекращается после grace period.

### 4.4. Редактирование

- Перетаскивание узла меняет только сохранённое положение.
- Создание связи: выбрать исходный узел → «Связать» → адресат → тип/направление/политика → сохранить черновик.
- Перенос в холон меняет владение с проверкой циклов, доступов, бюджета и активных запусков.
- Выделение рамкой/Shift → групповые действия «Назначить роль», «Добавить в холон», «Права», «Остановить», «Архивировать».
- Undo/redo относятся только к конфигурации черновика, не к выполненным внешним действиям.
- Удаление агента заменено архивированием; безвозвратное удаление находится в управлении данными.

### 4.5. Наблюдение

Click — выбрать; double click — открыть полный экран агента/погрузиться в холон. Hover показывает компактную подсказку без всего transcript. Esc снимает выделение/закрывает панель.

Click на активном ребре открывает сообщения между участниками с отправкой, доставкой, taskId и reply chain. Для агрегированного ребра показывается число сообщений и список исходных событий.

«Только соседи», «Только активные», фильтр по роли/ошибкам и поиск ID позволяют найти конкретный экземпляр среди тысяч.

### 4.6. Масштаб графа

До 50 узлов — подписи всех узлов при достаточном месте. 50–500 — подписи выбранных, активных и релевантных; раскрытие остальных по hover. 500–5000 — свёрнутые холоны по умолчанию, стабильные координаты, виртуализированный список, видимые на экране узлы и рёбра.

Каждый агент сохраняется в модели даже при агрегации. Контейнер «Холон · 1000» не выдаётся за единственный агент. Поиск раскрывает путь к нужному ID.

Автораскладка запускается пользователем или при первичном создании и работает вне UI-потока. Текущие узлы не «плавают» постоянно. Dragged/pinned positions сохраняются.

При большом потоке допускается агрегирование анимаций по паре узлов в окне 250 ms с числом событий. Надёжный журнал при этом не агрегируется и не теряется.

## 5. UI-04. Архитектура

Открывается как отдельная широкая панель с превью топологии. Верх — пресет, имя системы, ревизия. Три секции:

1. **Состав:** дерево холонов, таблица ролей с количеством, общий N. Ввод 1000 не создаёт процессы до запуска.
2. **Управление:** независимые переключатели «ИИ-координатор» и «Общая память», назначение узла/подключения и правило dispatch.
3. **Ресурсы:** C, max instances, per-account concurrency, budget, предел делегирования и scaling rules.

Ниже — «Проверить архитектуру»: циклы владения/DAG, missing role, связь вне ACL, недоступный required MCP, C>N, неназначенный coordinator, недостижимый обязательный участник.

Сохранение: «Сохранить черновик»; после успешной проверки «Использовать в следующем запуске». Для текущего run — только явная операция миграции на границе turn, если поддерживается.

При отключении памяти: список затронутых ролей/задач, выбор замены либо блокировки required задач. Уже прочитанные данные не исчезают из контекста.

При N=1 приложение автоматически предлагает прямой dispatch; не добавляет координатора и холон-обёртку.

## 6. UI-05. Роли и экземпляры

Вкладки раздела: «Экземпляры» и «Роли». Таблица экземпляров виртуализирована: выбор, имя, ID, роль@версия, холон, runtime, состояние, task, host. Сортировка, поиск, фильтры, настройка колонок.

Редактор роли: инструкция слева; параметры и preview справа. Обязательные поля помечены; валидация рядом с полем. Составная инструкция доступна для просмотра без секретов: политика системы, роль, задача, релевантные сообщения, ссылки на знания.

Мастер массового создания:

1. Выбрать роль/версию или создать новую.
2. Ввести N, шаблон имени и холон.
3. Задать права и источники; показать унаследованные ограничения.
4. Настроить C и правила.
5. Предпросмотр итоговых экземпляров, ресурсов и предупреждений.
6. «Создать N экземпляров»; затем отдельное «Запустить задачу».

Нумерация может начинаться с заданного индекса, но ID всегда генерирует приложение. Повтор шаблона имени не допускает неоднозначных display names в одном owning holon.

Групповая смена роли показывает выбранные экземпляры и новую версию. Для работающих — «Применить со следующего запуска». Групповые права вычисляются как пересечение ограничений, а не как объединение разрешений.

## 7. UI-06. Инспектор/страница агента

Заголовок: имя, роль, ID с copy, состояние, кнопки task/pause/stop. Вкладки:

- **Обзор:** задача, холон, версия роли, runtime/session/host, длительность, потребление, краткий прогресс.
- **Чат:** сообщения пользователя и видимые ответы/сводки агента, очередь следующего turn, вложения.
- **События:** план, инструменты, файлы, ошибки, сообщения; доступны raw metadata без секретов.
- **Связи:** разрешённые адресаты, реальные недавние обмены, неотвеченные вопросы.
- **Знания:** источники, реально использованные ссылки, созданные утверждения.
- **Результаты:** артефакты, версии, diff, acceptance.
- **Настройки:** role binding, budgets, permissions, MCP, effective configuration.

Пользовательский чат с агентом не становится глобальным автоматически. В каждом composer виден получатель; смена получателя не переносит приватную историю без явного выбора.

Кнопка «Сводка хода работы» запрашивает краткое объяснение действий и доказательства, если это нужно; она создаёт отдельный видимый запрос и может расходовать лимит.

## 8. UI-07. Задача и запуск

Полноэкранная форма для сложной задачи и компактный composer для простого сообщения используют одну модель данных.

Поля: цель, адресат/dispatch, input attachments, output format, acceptance criteria, deadline, budget, required tools, priority, stop policy. Advanced содержит DAG и strategy.

Перед стартом — небольшой review: ревизия архитектуры, количество адресатов, C, доступные runtime, required MCP, права записи, предполагаемые внешние действия. При валидной конфигурации запуск требует одного действия «Начать».

Прогресс: список подзадач/этапов с исполнителями, параллельно доступен граф. Панель «План» показывает исходный план и версии изменений. Оператор может отменить конкретную ветку.

Для запроса семантического анализа всей системы без координатора UI предлагает назначить одного из существующих агентов на эту задачу или вернуть отдельные результаты без синтеза.

Результат имеет кнопки «Принять», «Вернуть с замечанием», «Продолжить», «Экспортировать». Требования качества и артефакты видны рядом.

## 9. UI-08. MCP

Каталог и настроенные подключения разделены вкладками. Строка: иконка, название/издатель, transport, статус, область, число bindings, required usage, toggle, меню.

Три независимых признака:

- **Желаемое включение:** пользователь разрешил использовать сервер.
- **Здоровье:** проверен, degraded, auth_required, offline, unknown.
- **Доступ агента:** конкретный allowlist/binding с revision.

Переключение ON без настроек открывает мастер. На ошибке toggle возвращается OFF, введённые несекретные поля сохраняются. Если уже включённый сервер временно недоступен, ON остаётся как желание, рядом красный/янтарный статус «Нет связи»; зелёное состояние не показывается.

Мастер: «Рецепт/сервер → Доступ → Проверка → Привязки». У каждого поля есть пример, источник значения, кнопка инструкции и конкретная ошибка. Ключи/пароли вводятся в защищённые поля и после сохранения не выводятся обратно.

Диагностика отдельно показывает процесс/HTTP, handshake, авторизацию, tools/list и контрольную разрешённую операцию. Проверка read-only не пишет тестовый документ.

При OFF новые вызовы блокируются сразу в gateway. Текущая операция получает cancel, если поддерживается; иначе ждём ограниченный timeout и показываем состояние. Перед следующей выдачей turn конфигурация агента обновляется.

Полные инструкции рецептов — [04-integrations.md](specs/04-integrations.md).

## 10. UI-09. Знания

Левая часть — источники и namespace, центр — документы/поиск/граф, справа — provenance. Статусы: найден, загружается, разбирается, индексируется, готов, устарел, ошибка, неподдерживаемый формат.

Добавление источника не равняется предоставлению его всем ролям. Мастер спрашивает владельца и bindings. Для large folders сначала оценка количества/размера и исключения; скрытые системные каталоги исключены.

Утверждение имеет источник, цитату/фрагмент при допустимом размере, источник даты, агента-автора и связанные проверки. Отдельные состояния «Предложено», «Подтверждено правилом/человеком», «Оспорено», «Устарело».

Поиск возвращает ссылки с версией документа. При недоступности источника пометка о stale cache и действующей политике чтения.

## 11. UI-10. История запусков и replay

Таблица: цель, дата, состояние, архитектура@revision, число агентов, длительность, расход с типом известности, принятые артефакты.

Открытие run показывает временную шкалу, DAG, граф, события и результаты на момент запуска. Переключатель «Запись / Сейчас» меняет read model; replay всегда снабжён значком записи и не разрешает отправку команд.

Replay: play/pause, 0.5×/1×/2×/4×, scrubber, переход к ошибке/сообщению. В демо доступна сокращённая иллюстрация; production replay восстанавливается из журнала с sequence/cursor.

«Повторить» создаёт новый run с новым ID. Выбирается исходная или текущая конфигурация; внешние эффекты исходного run не воспроизводятся скрытно.

## 12. UI-11. Исполнители и ресурсный план

Карточка локального/удалённого worker: имя, OS, версии runtime, доступность, heartbeat age, ресурсы, вместимость, allocated/running slots, состояние drain.

Карточка аккаунта: способ входа, имя/маскированный идентификатор, доступность модели, общий concurrency cap, наблюдаемый quota status. Отдельный API-ключ не называется подпиской.

План запуска 1000: requested slots, schedulable slots, hosts, bottlenecks, очередь и стратегия start_all/queue_allowed. Все оценки помечаются расчётами; невыявленные provider limits отображаются как неизвестные.

Перенос экземпляра между hosts требует доступных артефактов, совместимой сессии и новой авторизации на целевом host. Автоматического копирования auth.json нет.

## 13. UI-12. Центр решений и ошибок

Один inbox для запросов человека, approval и эскалаций. Запрос содержит агента/задачу, точное действие, цель, объём данных, последствия, срок и доступные решения.

Разрешение связывается с attempt + tool + arguments hash + resource scope; изменение аргументов требует нового разрешения. Запоздалое разрешение отменённого attempt отклоняется.

Технические ошибки имеют «Что произошло», «Что сохранено», «Что можно сделать». Кнопки: повторить безопасную операцию, изменить настройку, переназначить, открыть журнал, отменить.

Нет массового автоматического разрешения неизвестных команд. Безопасное повторение уже разрешённой идентичной операции возможно по политике; scope виден.

## 14. UI-13. Настройки

Тема, русский/английский, reduced motion, видимость ID, retention, резервные копии, пути, защита секретов, runtime versions, обновления, proxy/CA, диагностика.

Экран восстановления: список снимков, версия схемы, дата, размеры, проверка целостности, preview remap путей, состояние секретов. Восстановление выполняется в новую рабочую область до проверки результата.

Командные настройки добавляются в отдельном выпуске: пользователи, роли, worker identities, budgets, audit export.

## 15. Общие состояния и доступность

Каждый экран обязан иметь loading, empty, error, stale/offline и partially available. Spinner ограничен timeout; бесконечное ожидание заменяется конкретным статусом.

Текстовый интерфейс остаётся рабочим без графики WebGL. Контраст основного текста ≥ 4.5:1; для крупных надписей и контуров UI ≥ 3:1. Статус всегда выражается текстом/значком в дополнение к цвету.

Клавиатура: Ctrl+K палитра, Ctrl+Enter отправить, Shift+Enter новая строка, Esc закрыть, Ctrl+Z/Y черновик, F fit на холсте. Delete при фокусе узла открывает архивирование, в поле редактирует текст. Горячие клавиши не перехватываются в чужом контексте.

Для screen reader есть список узлов и таблица событий. Потоковый вывод не зачитывается посимвольно. Выделение в графе и строка списка синхронизированы. Focus trap и возврат фокуса после закрытия modal/drawer обязательны.

Минимальное окно 1280×800; при меньшей доступной области правый инспектор становится drawer, нижний журнал вкладкой. При масштабе ОС 200% приложение не теряет доступ к основным действиям.

# 03. Архитектура и контракты исполнения

Архитектурный baseline для реализации. Здесь «должен» означает требование продукта; наличие конкретной возможности внешнего исполнителя подтверждается отдельно.

## 1. Выбранный стек

| Слой | Решение | Причина и граница |
|---|---|---|
| Desktop shell | Tauri 2, Windows 11 x64 | Нативная упаковка, OS-интеграции, ограниченный IPC |
| UI | React + TypeScript, Vite | Компоненты сложного редактора, типизированные контракты |
| Граф | Sigma.js + Graphology, собственные слои состояний | WebGL для многих узлов; редактор форм и архитектуры остаётся DOM |
| Раскладка | Отдельный Web Worker | Расчёт не блокирует ввод; координаты сохраняются |
| Control/worker | Rust + Tokio | Процессы, ограниченные очереди, typed IPC, общий код daemon и worker |
| Локальные данные | SQLite, WAL, один логический writer | Транзакции конфигурации, задач и журнала; файл на локальном диске |
| Файлы | Content-addressed artifact store | Проверка hash, версионирование и перенос |
| Секреты | OS credential store; отдельный vault для managed server | Ссылки на секреты в конфигурации |
| Командная/cluster версия | Rust services, PostgreSQL, object storage, TLS worker API | Отдельная topology без общей SQLite по сети |
| Контракты | JSON Schema + сгенерированные TS/Rust модели | Независимость UI, адаптеров и тестов |

Версии зависимостей фиксируются lockfiles в фазе реализации. «Последняя версия» не является контрактом. Sigma.js выбран для рендеринга графа на WebGL по его официальной документации; сложные интеракции холонов должны пройти spike до окончательной фиксации. [Sigma.js](https://www.sigmajs.org/docs/)

Веб-клиент не получает shell или полный Tauri API. Для каждого окна/команды задаются разрешения и отдельная проверка аргументов на стороне Rust. Tauri capabilities — один уровень ограничения интерфейса, а не песочница для Codex. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)

## 2. Компоненты

Схема исполнения:

    Desktop UI
        │ типизированные команды / события
    Tauri bridge
        │ защищённый локальный IPC
    PolyMAS daemon
        ├── Configuration + revisions
        ├── Task planner + dispatcher
        ├── Scheduler + quotas + leases
        ├── Message router + inbox/outbox
        ├── Policy engine + approvals
        ├── Runtime adapter registry
        ├── Event journal + projections + replay
        ├── MCP gateway + connection manager
        └── Artifacts + knowledge metadata
                 │
             Worker supervisor
                 ├── Codex process for agent A
                 ├── Codex process for agent B
                 └── Codex process for agent N

Каждый Codex работает через собственный адаптерный контекст: runtimeProcessId, agentId, sessionId, attemptId, working directory, leaseEpoch. MCP gateway не становится общим «мозгом»; он проверяет и журналирует операции.

Daemon живёт отдельно от окна. Закрытие UI по умолчанию спрашивает один раз настройку «Оставлять задачи в фоне / останавливать». При фоне остаётся значок tray; после перезапуска UI подключается к тому же daemon. Удаление приложения сначала переводит daemon/worker в drain.

Локальный транспорт: named pipe с ACL текущего пользователя на Windows, domain socket с правами владельца на Unix. Не открывать публичный порт для локального режима. Командный сервер получает отдельный аутентифицированный HTTPS/WebSocket интерфейс; браузер не подключается к Codex напрямую.

## 3. Codex: два адаптера

### 3.1. CodexExecAdapter — исходный production-кандидат

Внешний процесс запускается через OS spawn с массивом аргументов, без shell-интерполяции. Найденный wrapper .ps1 не выполняется через собранную строку: resolver определяет проверенный реальный бинарник/entrypoint, записывает путь и версию.

Концептуальный первый запуск:

    codex exec --json --color never --sandbox read-only --cd <agent-workspace> -

Инструкция поступает в stdin. Права записи добавляются только по профилю workspace-write. Параметры конфигурации компилируются проверенным TOML-сериализатором. При использовании папки без Git явно применяется поддерживаемый skip-git-repo-check; наличие Git не считается безопасностью.

Фактический набор флагов проверяется для версии CLI. В частности, у установленной 0.144.1 справка resume не содержит все флаги первого exec: адаптер не переносит argv вслепую. cwd повторного процесса задаётся OS spawn; обязательная политика проверяется отдельно.

Первый thread.started возвращает providerSessionId, который атомарно связывается с agentId. Следующие turn используют **конкретный** session ID:

    codex exec resume --json <provider-session-id> -

Опция --last в продукте запрещена: при сотнях сессий она неоднозначна. Один session ID защищён single-writer lock.

JSONL stdout разбирается инкрементально; stderr направляется в ограниченный диагностический канал. Парсер обрабатывает частичные строки, UTF-8 на границе chunk, неизвестные поля, max frame size, завершение без terminal event.

Нормализуются thread.started, turn.started, item.started/updated/completed, turn.completed, turn.failed и error. События не обязаны содержать каждый токен ответа. UI не показывает посимвольный streaming, если CLI его не отдаёт. [Codex non-interactive](https://developers.openai.com/codex/noninteractive)

Успешный process exit сам по себе не подтверждает полезный результат. Требуются терминальное событие или корректно классифицированное завершение, сохранённый output и проверка результата. Если результат есть, но процесс завершился ошибкой, run получает partial/needs_review по политике.

Capabilities исходного адаптера:

| Capability | Поведение |
|---|---|
| separate_process | Да, один Codex на работающий экземпляр |
| explicit_session_resume | Да, после интеграционной проверки конкретной версии |
| structured_events | Да, наблюдаемые JSONL-события |
| streaming_text | Только при фактическом наличии delta; не обязательна |
| steer_active_turn | Нет; очередь следующего turn или interrupt |
| interactive_cli_approvals | Нет; не эмулировать stdin-ответы на TUI |
| platform_tool_approvals | Да, через PolyMAS gateway/operation workflow |
| hard_pause | Нет; пауза выдачи и interrupt |
| usage | Поля, фактически переданные CLI; остальные null |
| context_export/import | Не обещается; session resume локально, remote migration отдельно |

Продукт не использует dangerously-bypass-approvals-and-sandbox. Если политика действия не может быть обеспечена этим адаптером, действие недоступно до выбора подходящего изолированного профиля или другого адаптера.

### 3.2. CodexAppServerAdapter — отдельный экспериментальный профиль

Этот интерфейс подходит для встраиваемых клиентов и имеет thread/turn, события и запросы решений. Однако документация, полученная 08.09.2026, прямо обозначает app-server и WebSocket transport как экспериментальные и не поддерживаемые для production workloads. Использование не скрывается под production-кнопкой. [Codex App Server](https://developers.openai.com/codex/app-server)

Для spike: отдельный процесс app-server на каждый AgentInstance, локальный stdio, initialize → initialized → thread/start либо thread/resume → turn/start. Возможности turn/steer, turn/interrupt, approvals включаются только по схеме выбранной версии. Нельзя помещать 1000 агентов как 1000 threads одного процесса и выдавать это за 1000 Codex CLI.

Схемы генерируются самим выбранным бинарником через generate-json-schema/generate-ts и сравниваются при обновлении. Протокол app-server имеет собственный формат JSON-RPC-подобных сообщений; нормализованные PolyMAS events не копируют его как публичный API продукта.

Допуск в production требует изменения официального статуса поддержки или отдельного формального решения о принятии риска с поддерживаемой версией, тестами совместимости и rollback. До этого основной выпуск должен выполнять заявленные сценарии на exec с указанными ограничениями.

### 3.3. Общий контракт RuntimeAdapter

Операции: probe, validateProfile, startAttempt, resumeAttempt, sendNextTurn, interrupt, health, drain, collectArtifacts, readUsage, dispose.

Каждая возвращает результат или типизированную ошибку: unsupported_capability, invalid_config, authentication_required, rate_limited, provider_unavailable, sandbox_denied, protocol_error, process_crashed, timeout, cancelled, unknown_external_effect.

startAttempt принимает instance snapshot, task snapshot, resolved resources, secret handles, output schema и lease token. Адаптер не принимает произвольные команды из renderer.

Event stream выдаёт нормализованные события с сохранённым source_type и ссылкой на очищенное исходное событие. Unknown events сохраняются как runtime.unknown_event и не переводят состояние в успех.

## 4. Идентичность, роли и авторизация

agentId стабилен между процессами и независим от имени/номера. runtimeProcessId — UUID записи процесса, а OS PID хранится отдельно вместе с start time и worker bootId, чтобы избежать ошибок при повторном использовании PID.

Роль фиксируется как roleId + version + contentHash. В exec она компилируется в документированную инструкцию задачи/контекста. Не заявляется управление настоящим system message модели. Для доступа к shell/MCP ограничение задаётся политикой исполнения, а не текстом роли.

AuthProfile принадлежит аккаунту и host. Credentials предоставляет штатный механизм Codex. Нельзя размножать auth.json по папкам экземпляров или отправлять refresh token на удалённые hosts.

Для локальной группы агентов возможен общий app-owned CODEX_HOME авторизационного профиля при собственных workspace и session IDs. Auth/login/logout/refresh-sensitive операции сериализуются в credential manager; профиль не переписывается на каждом turn. Совместная работа нескольких CLI с этим профилем — обязательный smoke/spike G-02 до выпуска.

Если Codex самостоятельно обновляет токены вне контроля manager, совместимость его refresh/cache при параллельных процессах должна быть доказана. При отказах используется поддерживаемое разделение profiles/host authentication; самодельный протокол обмена OAuth-токенами не вводится.

Подключение существующего пользовательского Codex home требует явного выбора в мастере и проверки effective config. По умолчанию PolyMAS не меняет глобальный config.toml пользователя. Управляемые параметры передаются snapshot-конфигурацией; унаследованные внешние MCP не получают доступ автоматически.

CODEX_HOME и рабочая папка не заменяют OS sandbox. Для hostile или межпользовательских workloads нужен отдельный OS principal/container/VM, недоступные агенту credentials и файловые границы.

## 5. Машины состояний

### AgentInstance

configured → idle → queued → starting → running → idle.

Во время running возможны tool_wait, waiting_message, waiting_user, rate_limited. stopping → stopped; failed может вернуться queued только новой попыткой. archived исключён из dispatch.

Instance state — проекция runtime + текущей задачи. История завершённых задач не перезаписывается статусом следующей.

### Task / Run

draft → validating → queued → running → awaiting_acceptance → succeeded.

Дополнительно: blocked, paused, cancelling, cancelled, partial, failed. paused не обещает заморозку OS-процесса: это запрет новых turn/подзадач. cancel является идемпотентной командой.

### Attempt

reserved → launching → active → finalizing → succeeded/failed/cancelled/unknown.

Терминальное состояние неизменно; повтор — новый attempt ID. При process crash с неизвестным результатом внешнего действия запрещён blind retry.

### MCP connection

disabled → configuring → testing → ready → degraded/auth_required/offline.

enabledDesired хранится независимо от health. Отзыв binding действует немедленно, даже если старая capability ещё отображается в каталоге текущего Codex turn.

## 6. Планировщик и admission

Планировщик выдаёт одну активную попытку на агента и применяет одновременно:

- workspace/holon/run concurrency;
- worker capacity и reserve памяти;
- authProfile/provider concurrency;
- модельные/сервисные rate limits, если известны;
- бюджеты задачи, число turn, TTL и deadline;
- required MCP availability и права.

Дисциплина: weighted fair queues между run/holon, priority с aging, запрет starvation. Приоритет не отменяет бюджеты. Задача, ожидающая сообщение/человека, не должна постоянно держать модельный слот; в exec turn завершается структурированным ожиданием, потом продолжается новым процессом.

Стратегии admission:

- queue_allowed: регистрируются все задания, выдаются в пределах слотов;
- start_all: резервируются все нужные слоты либо запуск не начинается; reservation имеет TTL.

Лимиты аккаунта общие. При rate_limited новые attempts профиля приостанавливаются, Retry-After учитывается если доступен; иначе exponential backoff с jitter, верхним пределом и max retries. Отсутствующие сведения о квоте не считаются разрешением на 1000 запросов.

Stop workspace атомарно увеличивает generation, отменяет очереди и запрещает lease старого generation. Worker перед новым turn/tool сверяет generation и срок lease.

## 7. Доставка сообщений

Агентам доступен собственный платформенный MCP с инструментами PolyMAS, которые **будут реализованы приложением**, а не существуют в Codex:

| Инструмент | Семантика |
|---|---|
| polymas.send_message | Записать сообщение разрешённому адресату; вернуть durable receipt |
| polymas.list_inbox | Получить разрешённые сообщения с cursor |
| polymas.ack_message | Явно подтвердить обработку |
| polymas.request_task | Предложить подзадачу; policy проверяет DAG, assignee и бюджет |
| polymas.publish_artifact | Зарегистрировать файл/объект с hash и ownership |
| polymas.request_operation | Запросить действие, требующее решения человека |
| polymas.get_operation | Узнать состояние без блокирования на минуты |
| polymas.report_progress | Публичная краткая сводка с доказательствами, не скрытое рассуждение |

Identity берётся из доверенного соединения + capability token, а не из senderId, переданного моделью. Разрешения проверяются на каждое обращение.

Outbox и состояние задачи пишутся одной транзакцией. Доставка at-least-once с messageId и inbox unique key (recipientId, messageId). Получатель получает упорядоченный inbox; общего глобального порядка всех агентов не обещается.

В exec новые сообщения передаются во вход следующего turn. Перед запуском сохраняется inbox batch с attemptId; только после наблюдаемого старта и подтверждения подачи входа отмечается delivered_to_context. Если возникла неоднозначность, batch сохраняет uncertain_delivery и повторяется с теми же ID для дедупликации в прикладной обработке.

Ограничения по умолчанию: message body ≤ 64 KiB, fan-out ≤ 32, hops ≤ 8, срок ≤ 24 h, максимум 1000 сообщений на run, очередь inbox ≤ 10000 элементов. Большие результаты — artifact refs. Значения изменяемы администратором в рамках workspace ceiling.

Ожидание ответа: агент отдаёт wait condition, turn освобождает слот; scheduler возобновляет при новом релевантном сообщении/deadline. На timeout — эскалация, fallback либо ошибка по task contract.

## 8. MCP gateway и границы полномочий

Gateway удерживает connection pools, tool allowlist, namespace bindings, audit и операции approval. По умолчанию один gateway-service на worker, а не отдельный тяжёлый DB server на каждого агента. Подключения разделяются по tenant/auth/scope и совместимости transport.

Если сервер stateful или требует выделенного stdio, manager создаёт выделенный child process для соответствующего security context; sharing никогда не смешивает credentials или namespace.

Gateway выдаёт агенту короткоживущий ограниченный токен по защищённому каналу/окружению. Upstream secrets остаются у manager; при необходимости прямого stdio server они передаются только этому дочернему процессу, не общему окружению Codex.

MCP tool annotations readOnly/destructive — подсказки, не доказательство безопасности. Read-only обеспечивается allowlist, DB permissions, filesystem sandbox и network policy.

Proxy должен сохранять negotiated capabilities, отмену, pagination, ошибки, ресурсы и prompts только в поддерживаемом объёме. Неподдерживаемые sampling/elicitation/roots объявляются недоступными, а не молча ломаются. Полная совместимость с произвольным MCP не обещается.

Для approval в exec gateway быстро возвращает operation_pending + ID. Модель завершает turn в waiting_user. После решения выполняется новая попытка с exact argument hash; долгое ожидание не подвешивает MCP до tool timeout.

Любой прямой доступ к внешнему write endpoint в обход gateway блокируется изоляционным профилем, если требуется строгая проверка операции. В trusted-local режиме границы честно описываются; он не допускается как межпользовательская песочница.

## 10. События и API приложения

Envelope: schemaVersion, eventId, streamId, sequence, timestamp, observedAt, workspaceId, runId, taskId, agentId, attemptId, correlationId, causationId, type, payload.

Порядок гарантируется по streamId/sequence. timestamp источника и observedAt управляющего контура различаются: часы hosts могут расходиться. При reconnect клиент сообщает cursor; backend отправляет snapshot + suffix событий. Если cursor удалён retention, возвращает resync_required.

Надёжные события: жизненный цикл, сообщения, approvals, артефакты, результаты инструментов. Эфемерные: визуальные particles, промежуточные text deltas, CPU samples. При backpressure допустима потеря/сжатие последних, но не первых.

Публичные команды v1:

| Команда | Результат и семантика |
|---|---|
| workspace.create/import/export | Workspace или экспорт без секретов |
| role.saveVersion | Неизменяемая версия |
| agent.createBatch | operationId + список IDs после commit |
| architecture.validate/commit | Диагностики + revision; optimistic concurrency |

Transport desktop — IPC; remote service отображает эти операции на versioned HTTP endpoints и authenticated event WebSocket. Это собственный канал PolyMAS, не экспериментальный Codex WebSocket.

## 11. Надёжность и внешние эффекты

Перед launch scheduler атомарно резервирует task + agent + slot и выдаёт lease с monotonically increasing epoch. Heartbeat каждые 5 s; lease TTL 30 s как стартовый параметр. Worker прекращает новые действия при истечении lease и завершает принадлежащие ему процессы.

Потеря lease не доказывает, что прежняя внешняя операция не произошла. Fencing проверяется gateway, artifact registry и локальными write locks; произвольный внешний сервис может fencing не поддерживать. Тогда итог unknown_external_effect и ручная сверка/compensation.

После падения daemon: восстановить durable state → обнаружить свои child processes по bootId/PID/start time → восстановить допустимые соединения или завершить orphan → reconcile attempts → только затем выдавать новые lease.

Прогресс stdout пишется в локальный ограниченный spool при разрыве с control service. Переполнение сначала ограничивает выдачу новых задач; при угрозе потери надёжных событий worker переходит drain и сохраняет причину.

Повторить можно безопасное чтение, незапущенный процесс или внешнюю операцию с подтверждённым idempotency key. При timeout внешней записи сначала status/reconciliation, не автоматическое повторение.

Windows supervisor применяет Job Objects для принадлежащих приложению деревьев процессов; Unix — process groups с grace и kill. OS resume/reboot тестируется отдельно. Нельзя завершать чужой процесс по одному совпавшему PID.

Диск full: запрет новых launch, попытка сбросить журнал, ограниченный аварийный audit, понятное состояние. Terminal success не подтверждается, если результат не сохранён.

## 12. Безопасность, данные и доступы

Threat model: вредоносный документ, MCP tool description/result, команда модели, скомпрометированный сервер, ошибочный оператор, другой tenant/worker.

Данные и сообщения рассматриваются как контент, не как распоряжения изменить политику. Составные промпты маркируют происхождение. Запрет расширения полномочий обеспечивается вне LLM.

Минимальные права filesystem/network, canonical paths, запрет traversal и выходов через symlink/junction, ограничение размера/времени, проверка URL/redirect destination, TLS для remote, secrets redaction до сохранения в логи.

Worker bootstrap использует одноразовое enrollment и короткоживущие identity credentials; tokens можно отозвать. UI users командного режима: viewer только читает, operator запускает/останавливает разрешённое, editor меняет конфигурацию, admin управляет доступом/секретами.

Markdown и tool output санитизируются; скрипты, локальные file URL и внешние загрузки не исполняются в renderer. Превью артефактов отделено от privileged window.

MCP authorization и учётные данные должны соответствовать выбранной версии протокола; bearer token не пересылается между сервисами с другим audience. [MCP authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

Retention по умолчанию: подробные run events 30 дней, диагностика 7 дней, конфигурация/принятые артефакты до удаления пользователем; срок изменяем. Экспорт данных и purge затрагивают индексы, кэш и backups по объявленному lifecycle. Удаление из локальной памяти не обещает удаления из провайдера.

## 13. Масштабирование до тысяч

Один управляющий проект может описывать N=5000 при малом C. Процессы запускаются лениво, каждый экземпляр сохраняет независимое состояние. Массовое создание не требует 5000 терминальных окон.

Для C=1000 scheduler распределяет 1000 выделенных Codex процессов по совместимым workers. Требования к ресурсам выводятся из benchmark RAM/CPU/process count и provider quota; количество hosts не фиксируется произвольно.

Не рассылать полный transcript каждому агенту. Контекст содержит роль, текущую задачу, bounded inbox и релевантные artifact refs. Сводки сохраняют provenance и явно маркируются как сжатые.

UI получает viewport/holon projections, delta batches не чаще 10–20 Hz, анимирует локально через requestAnimationFrame. История страницами; текстовый stream не вызывает rerender всех узлов.

Последовательность масштабирования: реальные 1 → 10 → 50 → 100 процессов, затем сертификационный C=1000 на разрешённом аккаунте/инфраструктуре. Симулятор на 5000 событийных агентов проверяет граф и очереди, но не считается проверкой 5000 CLI.

# 04. Codex и MCP: настройка, диагностика, рецепты

Этот документ описывает будущие мастера приложения. Приведённые команды — инструкции для реализации и самостоятельной настройки, они не выполнялись в рамках подготовки спецификации.

## 1. Подключение Codex CLI

### Что видит пользователь

«Настройки → Исполнители → Добавить → Codex CLI».

1. Приложение находит установленный Codex, показывает путь и версию.
2. Если его нет, кнопка открывает [официальное руководство CLI](https://developers.openai.com/codex/cli). Встроенная установка скачивает только зафиксированную поддерживаемую поставку после выбора пользователя; не меняет глобальную установку автоматически.
3. Выбирается рабочая папка и профиль изоляции.
4. Выбирается способ входа.
5. Проверяются доступность CLI, авторизация и отдельно реальный запрос.

### Вход через ChatGPT

Пользователь нажимает «Войти через ChatGPT». Приложение запускает штатный codex login в собственном auth profile, открывает полученный официальный URL и ожидает завершение. Пароль ChatGPT вводится только на странице входа. Headless/device flow предлагается только при поддержке выбранной версии и окружения.

После входа UI показывает метод и состояние из доступной диагностики Codex. Сам факт наличия файла credentials не считается успешной авторизацией.

### Вход через API-ключ

1. Открыть [страницу API keys](https://platform.openai.com/api-keys) в своём OpenAI Platform аккаунте.
2. Создать ключ в нужном проекте с минимальными правами.
3. Вставить в защищённое поле PolyMAS; сохранить в OS credential store.
4. Выполнить проверку. Передача ключа Codex — штатным механизмом, например stdin для login --with-api-key, без помещения значения в argv или лог.

ChatGPT-вход и API-вход поддерживаются Codex для локальной работы; использование API тарифицируется отдельно от включённого доступа ChatGPT. Приложение не обещает наличие конкретной модели или объёма квоты до проверки аккаунта. [Codex authentication](https://developers.openai.com/codex/auth)

### Диагностика и ограничения

Состояния: not_installed, incompatible_version, not_authenticated, auth_detected, verified_request, quota_blocked, network_error, managed_policy_denied.

В продукте хранится собственная матрица adapter × CLI version × OS × auth method. Непроверенная версия получает статус «Совместимость не проверена» и не подменяется известной. Автоматическое обновление CLI во время run запрещено.

История и runtime-state привязаны к explicit session ID. Отдельные экземпляры не получают случайную последнюю сессию.

## 2. Общая модель MCP-подключения

MCP-сервер предоставляет инструменты/ресурсы; база, файловое хранилище или внешний сервис находятся за ним. «MCP Neo4j» и «Neo4j database» — два компонента, у которых могут быть разные адреса и ошибки.

Поддерживаемые базовые transports Codex: локальный STDIO и Streamable HTTP; для HTTP возможны bearer token/OAuth. Конфигурация сервера и его enabled/required/tool allowlist должны соответствовать конкретной поддерживаемой версии. [Codex MCP](https://developers.openai.com/codex/mcp)

Внутренняя модель:

| Поле | Назначение |
|---|---|
| id, recipeId, recipeVersion | Стабильная идентичность и закреплённый рецепт |
| publisher, sourceUrl, verifiedAt | Происхождение и дата проверки инструкции |
| transport | stdio или streamable_http |
| command/args/cwd | Только для локального процесса; без shell parsing |
| url/authMethod | Для HTTP; HTTPS для удалённого адреса |
| secretRefs | Ссылки на защищённые значения, не сами значения |
| enabledDesired, health | Желание пользователя и наблюдаемое здоровье |
| tools/capabilities | Выявленные возможности и версия protocol |
| bindings | Субъекты, namespaces, allowlist, read/write, required |
| timeouts, poolLimits | Ограничения ресурсов |
| setupGuide | Шаги, ссылки, источники каждого поля и тесты |

Сервер с динамическим набором инструментов перепроверяется. Добавление нового tool не расширяет allowlist ранее сохранённого binding.

## 3. Поведение переключателя

1. OFF → пользователь нажимает ON.
2. Если нет обязательных полей/credentials, открывается мастер; включение ещё не сохранено.
3. Приложение показывает, что будет запущено/какие адреса использованы.
4. Проверяет configuration syntax → transport → MCP initialize → auth → capabilities → разрешённую контрольную операцию.
5. Пользователь выбирает роли/агентов/холоны и права.
6. Транзакционно сохраняются enabledDesired и bindings. Только теперь появляется «Подключено».

Сохранённое включение с потерянной связью: ON + «Недоступно». Отключённое: OFF + «Отключено». Отозванные credentials: ON + «Нужен вход»; вызовы blocked.

OFF во время работы: немедленно запрет новых вызовов; отмена поддерживаемых in-flight; список зависимых задач. Для required подключения задачи переходят blocked. Старая история не удаляется.

В UI не смешивать «сервер настроен», «проверка успешна», «сервер включён» и «доступ выдан этому агенту».

## 4. Рецепт A: файловое хранилище

**Цель:** агенты читают знания из выбранной пользователем папки.

### Пошаговая инструкция в продукте

1. Открыть «MCP → Файлы → Настроить».
2. Нажать «Выбрать папку» и указать каталог знаний. Рекомендуется отдельная папка проекта. API-ключ для локальной папки не нужен.
3. Выбрать «Только чтение» и допустимые форматы. Системные каталоги и секреты не выбираются по умолчанию.
4. Подтвердить источник/версию устанавливаемого файлового MCP или выбрать существующий сервер.
5. Нажать «Проверить»: список разрешённых корней и чтение одного выбранного файла.
6. Выдать доступ конкретным ролям/холону. Нажать «Подключить».
7. При необходимости открыть «Знания → Индексация». Доступ к файлам уже возможен, индекс создаётся отдельно.

Референсный MCP — @modelcontextprotocol/server-filesystem. Он умеет и чтение, и запись; передача allowed directory сама по себе не делает сервер read-only. Ограничение roots обязательно: сервер требует хотя бы один разрешённый каталог. Если поддерживается Roots, клиент управляет ими; этот набор должен формироваться gateway из политики, а не из ответа модели. [Filesystem server](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/README.md)

Read-only binding разрешает только обнаруженные инструменты чтения/списков/метаданных. Сервер запускается с файловыми правами чтения, если требуется строгая граница. Write tools отсутствуют в каталоге агента.

Проверки пути: canonical path, junction/symlink, UNC/съёмный диск, смена корня между проверкой и чтением. Для portable export путь заменяется alias knowledge_root.

Ошибки: папка отсутствует; нет OS-доступа; файл слишком большой; формат не поддержан; каталог вышел за разрешённый root; MCP binary отсутствует. У каждой ошибки своя кнопка исправления.

## 5. Рецепт B: Neo4j как графовая память

### Вариант B1: существующая БД и локальный MCP

Пользователь выбирает «Neo4j → Локальный MCP». Мастер объясняет: «Сервер MCP будет работать на этой машине и подключаться к указанной базе».

1. Открыть консоль/панель своей базы Neo4j. Если базы ещё нет, перейти по ссылке «Создать/установить Neo4j»; это отдельный сервис, возможные расходы не скрываются.
2. Взять адрес подключения, имя базы и credentials пользователя этой базы. При отсутствии прав создания ограниченной учётной записи обратиться к администратору базы.
3. В PolyMAS заполнить «Адрес БД», «База», «Пользователь», «Пароль». Пароль сохраняется в credential store. Для графа по умолчанию включено «Только чтение».
4. Выбрать установленный Python environment/MCP runtime либо установить закреплённый рецепт в изолированную среду PolyMAS.
5. Проверить запуск MCP и доступность БД по отдельности.
6. Выбрать namespace/схему знаний, разрешённые tools и участников. Для общей памяти нажать «Использовать как общую память» — это отдельная привязка.

Официальный self-hosted quickstart использует пакет neo4j-mcp-server и запуск python -m neo4j_mcp_server. Рецепт должен закрепить проверенную версию пакета; naked latest-install не используется в production. [Neo4j quickstart](https://neo4j.com/docs/mcp/current/quickstart/)

Поля рецепта преобразуются в NEO4J_URI, NEO4J_DATABASE, NEO4J_USERNAME, NEO4J_PASSWORD; read-only задаётся NEO4J_READ_ONLY=true. Пароль разрешается только дочернему MCP-процессу. В этой конфигурации при старте проверяются подключение и APOC; мастер должен показать отдельную причину, если зависимость отсутствует. [Neo4j configuration](https://neo4j.com/docs/mcp/current/configuration/)

**Не путать:** адрес neo4j+s://… — адрес базы, а не HTTPS MCP endpoint. Мастер отклоняет неправильный протокол поля.

### Вариант B2: Neo4j Aura / уже опубликованный HTTP MCP

1. Открыть Aura Console и сведения нужного instance.
2. Скопировать MCP URL из сведений экземпляра, если функция доступна. Документация приводит шаблон https://<INSTANCE_ID>.mcp-instances.neo4j.io.
3. В PolyMAS выбрать «HTTPS MCP», вставить endpoint; поля локального Python/NEO4J_PASSWORD env скрываются.
4. Выбрать поддерживаемый способ авторизации, который сообщает сервер/его инструкция: OAuth, bearer либо поддерживаемая gateway схема. Произвольный database password не подставляется автоматически как bearer token.
5. Пройти авторизацию, проверить tools, выполнить разрешённое чтение, назначить bindings.

Доступность Aura MCP для конкретного instance проверяется при настройке. [Neo4j Aura quickstart](https://neo4j.com/docs/mcp/current/quickstart/)

HTTP-режим Neo4j использует request authentication; переменные имени/пароля для STDIO не переносятся на него как универсальная конфигурация. [Neo4j HTTP authentication](https://neo4j.com/docs/mcp/current/authentication/)

### Семантика общей графовой памяти

Простое подключение Neo4j не создаёт готовую память. PolyMAS определяет namespace и типы Document/Claim/Entity/Source/AgentContribution, индексы, provenance и процесс верификации. Инициализация схемы является отдельной write-операцией с просмотром изменений.

Чтение — основной default. Публикация утверждений проходит app-level operation с проверкой namespace, источника и ACL. Raw arbitrary Cypher не используется как безопасная универсальная запись.

Read-only флаг и скрытие write tools дополняются правами DB principal. Разделение namespaces только фильтром промпта недостаточно. Если выбранная редакция/сервер не обеспечивает требуемую изоляцию, используются отдельная база или приложение-посредник.

## 6. Рецепт C: своя БД / PostgreSQL

Первый выпуск предлагает **«Свой MCP-сервер»**. Специализированный PostgreSQL-рецепт добавляется только после выбора издателя, версии и тестов. Образ карточки PostgreSQL на дизайн-референсе — направление каталога, не обещание встроенного проверенного драйвера.

Пользователь получает инструкции:

1. Выбрать поддерживаемый MCP-сервер для своей БД у его издателя.
2. Создать отдельного пользователя с минимальными правами у администратора БД.
3. Настроить сервер согласно его официальному руководству.
4. В PolyMAS добавить STDIO команду/аргументы или HTTPS endpoint.
5. Связать защищённые поля с именами переменных/headers, которые требует именно этот сервер.
6. Выполнить read-only probe и назначить allowlist/namespace.

PostgreSQL connection string не вводится в поле MCP URL. Поля БД должны принадлежать конкретному recipe, иначе wizard показывает обобщённые параметры сервера.

## 7. Рецепт D: удалённое файловое/объектное хранилище

Через «Свой MCP» подключаются серверы для файлового сервиса или S3-совместимого storage. До выбора конкретного сервера приложение не обещает универсальный access key format.

Wizard указывает: где в консоли выбранного поставщика выдать read-only доступ, какие bucket/folder prefixes разрешены, какой endpoint скопировать и какая версия MCP поддерживается. Секреты не записываются в URL.

Контрольная операция читает метаданные/выбранный объект. Большие объекты не целиком загружаются в контекст; используется ограниченный fetch/parser с artifact references.

Для Google Drive/аналогичных сервисов используется штатная OAuth-страница сервиса; пароль не вводится в PolyMAS. Доступ к каталогу и индексация — разные опции.

## 8. Рецепт E: произвольный MCP

Вкладки STDIO / HTTPS. Обязательные поля STDIO: путь к executable, массив args, cwd; HTTP: URL, поддерживаемый auth method. Advanced: env handles, headers from secret refs, timeout, proxy/CA, tool policy.

Свободное поле «вставьте команду» может быть удобным импортом, но до сохранения преобразуется в видимый executable + args, проходит разбор и подтверждение происхождения. Shell operators не исполняются.

Импорт JSON/TOML показывает diff. Нельзя молча выполнить неизвестный npx/uvx download. Каталог имеет pinned package version/checksum, список permissions, документацию и дату проверки. Community connector явно отличается от verified recipe.

Тестирование не выполняет неизвестные write tools. Неизвестный tool классифицируется как требующий явной политики.

## 9. Секреты и ротация

Секрет создаётся в vault, connection хранит secretRef. Renderer видит маску и наличие, не получает сохранённое значение. Значения не входят в экспорт архитектуры, промпты, history и диагностический bundle.

При ротации создаётся новая версия secretRef, проверяется тестовое соединение, новые turn переключаются на новую версию. Старый секрет отзывается после drain или немедленно при компрометации.

OAuth отмена возвращает мастер в исходное состояние. Callback проверяет state/PKCE и допустимый origin в соответствии с используемой библиотекой/протоколом. Не поддерживаемый flow означает понятный отказ, а не ручное копирование чужих токенов.

Кэшированные знания сохраняются только по retention/ACL. Отзыв source binding блокирует будущие чтения, но не удаляет автоматически уже включённый в provider session текст.

## 10. Диагностическая матрица

| Сбой | Сообщение пользователю | Действие системы |
|---|---|---|
| executable not found | «Не найден сервер MCP» | Предложить путь/установку recipe |
| invalid config | «Проверьте поле …» | Не запускать процесс |
| transport timeout | «Сервер не ответил» | Ограниченный retry, safe logs |
| handshake mismatch | «Версия протокола не поддерживается» | Показать совместимые версии |
| 401/auth missing | «Нужно войти или обновить ключ» | Остановить новые обращения |
| 403 | «Учётной записи не хватает доступа» | Не повторять login бесконечно |
| tools empty | «Сервер доступен, инструменты не предоставлены» | Проверить permissions/capabilities |
| DB unavailable | «MCP запущен, база недоступна» | Проверить адрес/сеть/сертификат |
| root denied | «Файл вне разрешённой папки» | Отклонить; не расширять root |
| timeout after write | «Результат операции неизвестен» | Reconciliation до retry |
| revoked during run | «Доступ отозван» | Блокировать новые вызовы, обновить bindings |

Каждый готовый рецепт проходит ту же матрицу в CI и интеграционном стенде. Инструкция «куда зайти и что вставить» поставляется вместе с recipeVersion и обновляется независимо от ядра приложения.

# 05. Spec-driven development, проверки и выпуск

## 1. Источник истины и процесс изменений

Порядок разрешения противоречий: согласованное требование пользователя → принятая версия продуктовой спецификации → контракт/ADR, согласованный с ней → UX → код → визуальный референс. Изображение не меняет семантику production.

Спецификация 0.1.0 — исходное предложение, подготовленное для ревью, а не свидетельство реализованного приложения. Реализация начинается вертикальными срезами, каждый из которых ссылается на FR, UI, INV и AC.

Для каждого среза:

1. Уточнить требуемое поведение и границы в spec change.
2. Обновить контракт, state transitions и ошибки.
3. Зафиксировать влияющее архитектурное решение ADR.
4. Определить проверяемые acceptance scenarios и fixtures.
5. Реализовать минимальный полный путь UI → backend → реальный исполнитель.
6. Проверить контракт, интеграцию и пользовательский путь.
7. Записать evidence: версии, стенд, команды/сценарии, результаты, известные ограничения.
8. Обновить статус FR и release notes. Не объявлять выполненным требование по одному screenshot.

Новая потребность сначала изменяет spec; несовместимый контракт получает новую major schema/API version. Миграции сопровождаются backup/restore test. Не использовать «TODO» в обязательном контракте принятого среза.

## 4. Проверки совместимости до глубокой реализации

| Gate | Вопрос | Проверяемое доказательство / fallback |
|---|---|---|
| G-01 | Работает ли exec/resume на выбранных Windows/CLI? | Два turn с explicit session ID, stream fixtures, Unicode/пути с пробелами; при отказе версия не допускается |
| G-02 | Можно ли безопасно разделять вход между выделенными CLI? | Параллельные 10 процессов, refresh/logout, отсутствие подмены сессий; при отказе поддерживаемые auth profiles или меньший C |
| G-03 | Как реально обеспечить instance filesystem/network policy? | Попытки чтения чужой папки/секретов и write вне root отвергнуты; для hostile workloads OS boundary |
| G-04 | Можно ли исключить скрытый встроенный spawn Codex? | Capability/config probe + task, пытающаяся spawn; если выключить нельзя, дочерние рантаймы выявляются и учитываются либо профиль отклоняется |
| G-05 | Достаточен ли Sigma для группировки и редактирования? | 5000 nodes, 25000 edges, hit test, layout worker, accessibility fallback |
| G-06 | Совместим ли MCP gateway с нужными servers? | Initialize/tools/resources/cancel/timeout/auth, без потери identity; unsupported capabilities обозначены |
| G-07 | Какой реальный process footprint и provider capacity? | Измерения 1/10/50/100, account throttling, projected C=1000 с резервом |
| G-08 | Можно ли допустить app-server в production? | Официальный статус и accepted ADR; иначе остаётся experimental |

Неопределённость G-02/G-03 не решается копированием auth.json или выключением sandbox. Экспериментальная функция не маскируется интерфейсом без предупреждения.

## 5. Приёмочные сценарии

| ID | Условие и действие | Ожидаемый результат |
|---|---|---|
| AC-01 | Чистая область → создать один экземпляр | Ровно один AgentInstance; нет скрытого координатора |
| AC-02 | Отправить локальную задачу агенту | Один выделенный Codex process, связанный attempt/session; JSONL отражён в UI |

## 8. Нагрузочные профили

1. **UI simulation:** 5000 instances, 25000 edges, 1000 events/s 15 min; burst 10000/s 10 s. Проверяет UI/backpressure, не Codex.
2. **Messaging:** 100000 уникальных сообщений, 10% дубликатов, 5% out-of-order; ожидается уникальный inbox и отсутствие утраты committed receipts.
3. **Process churn:** 1000 последовательных attempts на 10 slots; отсутствие orphan PID/дескрипторов, корректные role/session bindings.
4. **Real MAS:** 10 CLI обрабатывают разные задания в разных папках; сообщение, память, результат и cancel проверяются по OS/runtime logs.
5. **Real PolyMAS:** 1000 процессов одновременно выполняют контрольные короткие задачи и обмены, затем 8 h soak на разрешённом режиме. Реальное количество активных процессов фиксируется непрерывно, а не только число созданных IDs.
6. **Failure:** kill worker/control, timeout MCP, token expiry, revoked auth, disk full, network partition, duplicated lease, delayed approval, malformed UTF-8/JSONL.

Реальные provider-запуски не выполняются бесконтрольно из обычного CI. Контрактные fixtures и имитаторы отдельно помечаются; платные/подписочные integration jobs имеют выделенный бюджет.

## 9. Качество и тестовая стратегия

Domain tests — инварианты и переходы; property tests — ownership DAG, quotas, count preservation, message dedup; contract tests — схемы/CLI fixtures/MCP capabilities; integration — реальные process tree, SQLite/DB transactions и transports; e2e — критические пользовательские пути.

Визуальная проверка покрывает 3 референсных экрана, пустое состояние, 1/10/1000, ядро on/off, ошибка MCP, stale telemetry, 200% scaling и reduced motion. Pixel snapshot дополняет поведенческую проверку, не заменяет её.

Security проверки: secret leakage в экспорт/лог, prompt injection попытка расширить scope, path traversal/junction, cross-agent read/write, cross-tenant access, stale lease, arbitrary shell import, unsafe markdown.

Обновление Codex: pinned version → schema diff → adapter fixtures → real smoke → canary → rollout; при regression runtime version возвращается на поддерживаемую. Сессию новой версии не открывают старым CLI без проверки совместимости.

## 10. Production gate

Выпуск разрешён при выполнении обязательных AC текущего этапа, отсутствии блокирующих ошибок, проверенном installer/signing, SBOM/license inventory, backup/restore, rollback, диагностике и пользовательских инструкциях.

Каждый release содержит support matrix: OS, CLI versions, auth methods, tested N/C, MCP recipes, ограничения изоляции, ресурсы стенда, известные ограничения.

Smoke на локальной подписке не является доказательством права раздавать подписочный доступ внешним пользователям через hosted service. Для командной поставки проверяются актуальные условия выбранного провайдера и схема авторизации; не закладывается несуществующая лицензия на перепродажу.

Откат: остановить выдачу новых задач, drain, создать согласованный backup, переключить совместимую сборку, проверить миграции и session compatibility, возобновить. Разрушительный downgrade БД без backup запрещён.

## 11. Доказательства для сдачи этапа

Для каждой AC: дата, commit/build, spec version, environment, inputs, expected/actual, журналы без секретов, PASS/FAIL/SKIPPED, ссылка на issue для отклонения.

PASS ставится только по фактически выполненной проверке. Текущий пакет содержит проверку документов/макета/схем; проверки реального многопроцессного исполнения ещё не проводились.

# 06. Визуальная спецификация PolyMAS Studio

Версия 0.1.0. Дизайн настольного редактора и рабочего пульта. Три PNG задают направление; интерактивный макет уточняет основные взаимодействия. Ни один из них не является исполняющей платформой.

## 1. Визуальная идея

Тёмная рабочая область знаний с большим графом в центре, устойчивой навигацией и компактным контекстным инспектором. Агент — отдельный узел. Свечение используется только для наблюдаемой активности. Большая часть интерфейса спокойная, без непрерывного движения.

Заимствована идея пространственной навигации по знаниям, знакомая по Obsidian. Логотип, компоновка деталей, состояния и визуальные элементы PolyMAS самостоятельные.

## 5. Анимация и связь с событиями

- Running node: мягкая пульсация внешнего контура с периодом 1.8 s, не более 15% изменения opacity.
- delivered_to_context: точка вдоль ребра 600–1200 ms, направление from → to.
- tool call memory read: фиолетовый импульс к источнику; успешный ответ — обратный импульс.
- queued message: маленький значок ожидания у ребра/получателя, без эффекта уже доставленного сообщения.
- failed delivery: красный короткий штрих с ошибкой в журнале, без зацикленного мигания.
- selected node: постоянный контур, не собственная «работа».
- hover/панель: transitions 120–180 ms.
- reduced motion: никакой пульсации/движущихся частиц; статичные значки и число событий.

Проекция сохраняет состояние по event ID. Частицы могут агрегироваться, но число событий и журнал остаются точными. При stale heartbeat UI выключает активный эффект, пока связь не подтверждена.

Локальный макет позволяет:

Макет не читает файлы пользователя, не запрашивает API, не запускает Codex и не сохраняет секреты. Он предназначен для ревью структуры, плотности и логики основных контролов. Демо-счётчики и события явно обозначены; перезагрузка возвращает исходный сценарий.

Не все production-состояния интерактивно реализованы в макете. Полный контракт экранов находится в UX-spec; replay, RBAC, настоящий OAuth, виртуализация больших таблиц и восстановление — требования к будущему приложению.

## 10. Передача в реализацию

Сначала UI shell и дизайн-токены, затем доступный список/инспектор, затем граф с теми же read models. Нельзя реализовать вторую независимую модель данных внутри canvas.

Выбор/поиск, фильтры и команды отправляются общему UI store; изменения конфигурации проходят через backend validation. UI не считает успешным запуск/подключение по клику кнопки — только по подтверждённому событию.

Для каждого компонента сохранить примеры default/empty/error/stale и клавиатурного использования. Дизайн принимается по читаемости, точным состояниям и выполнению сценариев, а не только по совпадению PNG.

## Семантика blueprint

Population — инструкция массового создания, а не исполняющий агент и не общая история. При материализации каждого набора создаются count самостоятельных AgentInstance с постоянными UUID. Таблица соответствий populationId + ordinal → agentId сохраняется транзакционно.

Population count=1000 не допускает реализации 1000 виртуальных ролей в одном Codex. После admission запускаются отдельные процессы в соответствии с инвариантами спецификации.

coordinatorPopulationId ссылается только на набор из одного экземпляра. Его count включён в сумму N. Никакой дополнительный agentId не возникает из наличия холона.

Edge endpoint population:X задаёт разрешение для участников набора. Это не инструкция сделать broadcast. Dispatch определяет конкретных получателей отдельно; сообщение в runtime всегда имеет конкретные IDs.

auth:// и secret:// — внутренние ссылки на профили/секреты. Они требуют разрешения на целевой машине. modelSelection=runtime-default означает использование доступного default выбранного CLI без выдуманного имени модели.

## Валидация сверх JSON Schema

JSON Schema проверяет структуру. Domain validator обязан дополнительно проверять:

1. Уникальность IDs внутри каждого набора сущностей.
2. Существование roleId/roleVersion и connectionId у ссылок.
3. Общую сумму экземпляров 1–5000 и C ≤ N.
4. Ровно один экземпляр у координатора.
5. Отсутствие циклов владения холонов и единственного владельца population.
6. Корректность edge endpoints и ACL, отсутствие неподдерживаемого self-send.
7. При preset=single: N=1, C=1, без координатора; при star координатор обязателен.
8. При sharedMemoryConnectionId: существующее включённое подключение с подходящим binding.
9. Наличие доступного auth profile/runtime/required MCP при preflight.
10. Совместимость путей, sandbox, protocol versions и capabilities.

Runtime validation не заменяется проверкой JSON. Наличие корректного файла не подтверждает квоту или доступность инфраструктуры.

## Версионирование событий

sequence монотонен внутри streamId. Event ID уникален. causationId может ссылаться на другое событие; correlationId связывает сценарий целиком.

Строгие payload описаны для agent.state.changed, message.delivered, mcp.call.completed. Другие виды перечислены функционально в архитектуре и добавляются к схеме по мере принятия соответствующих срезов. Envelope сохраняет неизвестные типы, но consumer не должен трактовать их как успех или расширение полномочий.

Перед production каждого среза в контракт добавляются его конкретные request/response/payload schemas и negative fixtures. Это исходный набор контрактов, не утверждение о готовом полном backend API.
