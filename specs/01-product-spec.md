# 01. Продуктовая спецификация PolyMAS Studio

Версия 0.1.0 · 2026-09-08 · Предлагаемая исходная спецификация.

## 1. Назначение

PolyMAS Studio — настольный редактор, в котором пользователь проектирует, запускает и наблюдает системы ролевых ИИ-агентов. Агент может работать самостоятельно, взаимодействовать с другими агентами, обращаться к разрешённым источникам знаний и входить в холон. Холон может включать другие холоны.

Первый исполнитель — установленный Codex CLI. В дальнейшем добавляются Claude Code CLI и API-провайдеры через одинаковый контракт адаптера. Доступность функций каждого провайдера показывается явно. Интерфейс не обещает одинаковые возможности у разных исполнителей.

Исходная метафора — рабочая область знаний, знакомая по Obsidian, с живым графом экземпляров агентов. Результат работы системы — проверяемые сообщения, решения и артефакты. Граф объясняет, кто что делает и от кого зависит.

Слово «ROI» в исходном голосовом описании трактуется как «рой». Финансовая окупаемость не является обязательной метрикой продукта. Для эксплуатации нужны расход, время, качество результата и частота ошибок.

## 2. Предположения и границы

1. Первый целевой клиент: Windows 11 x64, русский интерфейс, настольная рабочая область. Архитектура допускает macOS/Linux и подключение удалённых исполнителей.
2. Начальная поставка: приложение одного локального пользователя. Командный сервер — последующая поставка с собственной авторизацией и разграничением доступа.
3. Данные и секреты по умолчанию остаются на машине пользователя; запросы модели уходят выбранному провайдеру, MCP-запросы — выбранным серверам.
4. «Локально» означает локальное управление процессами и файлами. Это не обещание работы облачной модели без интернета.
5. Создание спецификации не требует подключения аккаунта или запуска тысяч платных заданий. Все указанные показатели нагрузки — критерии будущей проверки.
6. Поддерживаемые версии Codex и MCP фиксируются перед каждым выпуском. Установленный при подготовке CLI: 0.144.1; проверены справки команд, реальные задачи в нём для этой спецификации не выполнялись.

## 3. Словарь и строгие инварианты

| Понятие | Определение |
|---|---|
| Рабочая область | Изолированный набор проектов, ролей, агентов, холонов, запусков, подключений и политик |
| Роль / RoleTemplate | Версионируемая инструкция, рекомендуемые инструменты, формат результата и правила работы. Сама роль не исполняется |
| Экземпляр / AgentInstance | Постоянный ID, закреплённая версия роли, собственные сессии, почтовый ящик, рабочая папка, права и состояние |
| Сессия | История диалога одного экземпляра с конкретным исполнителем. У агента могут быть последовательные сессии; активный turn не более одного |
| Процесс / RuntimeProcess | Один OS-процесс Codex для одного работающего экземпляра. После завершения turn процесс exec может закрыться |
| Попытка / Attempt | Одна попытка исполнения подзадачи; имеет свой ID, вход, результат и причину завершения |
| Холон / Holon | Группа агентов и/или вложенных холонов с внешним контрактом, границами доступа, бюджетом и правилом завершения |
| Запуск / Run | Исполнение конкретной задачи на неизменяемом снимке архитектуры и конфигурации |
| Топология | Разрешённые направления взаимодействия. Наличие ребра не означает факта общения |
| Сообщение | Явный объект с отправителем, получателями, типом, полезной нагрузкой и статусом доставки |
| Центральное ядро | Пользовательское сочетание необязательного ИИ-координатора и/или общей памяти |
| Координатор | Обычный агент с ролью маршрутизации/синтеза. Его процесс и расходы входят в общие числа |
| Общая память | Источник знаний, доступный определённым участникам; не модель и не агент |
| MCP-подключение | Настройка доступа к MCP-серверу; наличие подключения не даёт права всем агентам |
| Граф знаний | Сущности, утверждения, документы и связи с происхождением. Отдельный слой от графа агентов |
| Технический контур управления | Планировщик, журнал, политики и доставка. Работает без центрального ИИ |

**INV-01.** Два экземпляра никогда не имеют общий AgentInstance ID, записываемый mail inbox или активную сессию.

**INV-02.** В пределах одного attempt один живой процесс Codex принадлежит ровно одному агенту; уникальность обеспечивается lease и fencing token. Количество работающих агентов нельзя подменять количеством ролей или вызовов одной общей сессии.

**INV-03.** Завершение процесса не удаляет экземпляр. Повторный turn запускает новый выделенный процесс и продолжает явную сессию этого же агента.

**INV-04.** Любой запуск ссылается на зафиксированные версии роли, топологии, MCP bindings, политики, модели/адаптера и входных материалов.

**INV-05.** Ни модель, ни содержимое MCP/документа не может расширить права, бюджет или лимит экземпляров. Эти ограничения проверяет приложение вне модели.

**INV-06.** Общее число экземпляров включает координаторов. Оператор видит отдельно количество элементов графа и количество агентов: хранилища и холоны не увеличивают число процессов.

**INV-07.** Смена ядра не уничтожает историю, знания и созданные экземпляры.

**INV-08.** У каждой отображаемой активности есть источник события и время наблюдения; пропуск телеметрии не заменяется вымышленным событием.

**INV-09.** Отдельный процесс и отдельная папка сами по себе не являются границей безопасности. Приложение показывает фактический уровень изоляции.

## 4. Пользователи и основные задачи

| Пользователь | Требуемый результат |
|---|---|
| Автор системы | Создать роли, количество экземпляров, группы и допустимые связи без написания инфраструктурного кода |
| Оператор | Отправить задачу нужной части системы, видеть ход работы, вмешаться, принять результат |
| Разработчик интеграций | Добавить исполнитель или MCP-рецепт по контракту без изменения редактора |
| Администратор командной установки | Управлять исполнителями, правами, секретами, лимитами и аудитом |

Один человек может совмещать все эти роли. Интерфейс сначала показывает понятные действия; технические параметры находятся в раскрываемых настройках.

## 5. Функциональные требования

### FR-01. Рабочие области

Создать, открыть, переименовать, экспортировать и архивировать рабочую область. Шаблоны: «Один агент», «Команда с координатором», «Независимые агенты», «Несколько холонов».

Экспорт конфигурации исключает секреты и приватную историю по умолчанию. Импорт начинается с проверки схемы, совместимости исполнителей и путей. Восстановление привязок к секретам выполняется мастером.

### FR-02. Редактор ролей

Поля: название, описание, инструкция, ожидаемый результат, критерии завершения, допустимые получатели, правила эскалации, исполнитель, выбор модели, MCP, права файлов/сети, лимиты turn/времени/токенов.

Сохранение создаёт новую неизменяемую версию. Редактирование роли не меняет активные запуски. Предусмотреть diff двух версий, дублирование, откат путём новой версии и применение выбранным экземплярам со следующего запуска.

Инструкция роли не называется системным промптом провайдера, если адаптер не может установить системное сообщение. UI показывает способ применения инструкции: «передаётся во вход задачи» или «поддерживается отдельным полем исполнителя».

### FR-03. Создание экземпляров

Числовое поле задаёт любое допустимое целое N от 1; быстрые значения 1, 10, 100, 1000, 5000. Ползунок — вспомогательный, логарифмический; точное значение вводится клавиатурой.

Поля: версия роли, N, шаблон имён, холон, параметры по экземплярам, рабочая папка/режим файлов, bindings, initial session policy. Предпросмотр показывает первые экземпляры и итоговое число.

Массовая операция транзакционна на уровне определения: либо создаётся весь заданный набор, либо ни одного. Материализация папок/рантаймов — отдельный возобновляемый job с индивидуальными ошибками. Повтор команды с тем же idempotency key не создаёт дублей.

Дублирование экземпляра создаёт новый ID и новую историю по умолчанию. Копирование истории — отдельная операция fork с записью происхождения и без копирования секретов.

### FR-04. Численность и масштабирование

Два независимых поля: «Всего экземпляров N» и «Одновременно работают C». Всегда 1 ≤ C ≤ N для работающей системы; конфигурация без агентов допускается только как черновик.

Режимы:

- Фиксированное число: N стабильно.
- По очереди задач: добавить экземпляры заданной роли при устойчивом росте очереди.
- По правилам: условие → действие над желаемым числом экземпляров с жёсткими min/max.

Правило масштабирования не исполняет произвольный код. Пример: очередь роли > 20 в течение 60 секунд → +2 экземпляра, не чаще одного раза в 120 секунд, максимум 40. Уменьшение: очередь = 0 и агент idle > 10 минут → завершить свободный runtime и архивировать выбранный незанятый экземпляр, минимум 4. Сначала dry run с прогнозом изменений.

Саморепликация моделью запрещена по умолчанию. Агент может запросить расширение; policy engine ограничивает запрос теми же правилами. Встроенные subagents Codex не используются как незаметная замена отдельным экземплярам PolyMAS.

### FR-05. Холоны

Холон содержит собственную цель, участников, входной/выходной формат, приоритет, бюджет, политику общения, необязательную память и coordinatorAgentId.

Вложенность — дерево владения без циклов, до 16 уровней в первой модели. У агента один owning holon; участие в других задачах обеспечивается адресацией/связями, а не вторым владельцем.

Снаружи холон можно адресовать как единицу. Он раскладывает задачу по правилу dispatch и возвращает агрегированный результат. Это системная граница, а не дополнительный скрытый LLM. При семантическом синтезе назначается видимый агент-синтезатор.

Правила dispatch: один подходящий участник; явно перечисленные участники; все непосредственные исполнители; подзадачи по плану координатора. Рекурсивная широковещательная отправка всем потомкам требует явного выбора и показывает число адресатов.

### FR-06. Архитектуры и ядро

Предустановки:

| Режим | Координатор | Память | Маршрутизация |
|---|---|---|---|
| Один агент | Нет | Необязательна | Прямой turn одного Codex |
| Независимые | Нет | Отдельная или общая | Оператор назначает задачи; межагентные сообщения выключены |
| Сеть | Нет | Необязательна | Сообщения по разрешённым рёбрам |
| Звезда | Да | Необязательна | Координатор распределяет и собирает |
| Холоническая | На выбранных уровнях | На выбранных уровнях | Контракты групп и межгрупповые связи |
| Пользовательская | По конфигурации | По конфигурации | Редактируемый ориентированный граф |

Переключатели «ИИ-координатор» и «Общая память» независимы. Включение координатора предлагает назначить существующего агента или создать нового с явным увеличением N. Выключение удаляет привязку, но не удаляет агента.

Новая топология сохраняется как черновик; активный run продолжает старую ревизию. Отзыв доступа и аварийная остановка действуют немедленно как отдельные события политики. Опциональная миграция run допускается только между turn с просмотром затронутых задач.

### FR-07. Задачи и чат

Один composer поддерживает адресатов: отдельный агент, выбранная группа, холон, вся система. Поля задачи: формулировка, вложения/ссылки, ожидаемый результат, критерии приёмки, deadline, бюджет, приоритет, политика завершения.

Глобальная задача не рассылается автоматически каждому агенту. В режиме с координатором поступает координатору; без него — выбранному правилу dispatch. Перед запуском отображаются предполагаемые получатели и предел параллелизма.

Локальная задача привязана к выбранному ID и может выполняться независимо от соседей, если хватает ресурсов.

Чат — последовательность сообщений с контекстом выбранного адресата. Когда exec занят, новый ввод помещается в очередь следующего turn; доступна явная команда «Прервать и отправить». Вставка текста в середину исполнения обещается только адаптером с capability steer.

Задачи могут иметь зависимости DAG. Цикл зависимостей запрещён; обычная топология общения может содержать циклы и ограничивается TTL и бюджетами сообщений.

### FR-08. Правила распределения и завершения

Каждая подзадача имеет assignee, input snapshot, output contract и acceptor. Успешное завершение процесса — технический факт; приёмка результата — отдельное состояние.

Поддержать all_required, quorum, first_accepted и manual. Для quorum задаются k и число обязательных проверок; голос отсутствующего участника не считается положительным. first_accepted отменяет ненужные работы только после приёмки.

Автоматический план координатора проходит структурную проверку: существующие адресаты, корректный DAG, права, budgets, максимальное число дочерних задач. Изменение плана сохраняется новой версией.

«Задача завершена» означает, что выполнено выбранное правило приёмки, приложены результаты, нет обязательных незавершённых работ. Частично успешный запуск отмечается отдельно. Оценка «модель сказала готово» недостаточна.

### FR-09. Общение агентов

Типы: task_request, evidence, question, answer, critique, result, escalation. Каждое сообщение содержит sender, recipients, correlationId, causationId, replyTo, TTL, размер и ссылки на артефакты.

По умолчанию сообщение адресуется одному получателю или контракту холона. Broadcast ограничен fan-out, показывается в UI и расходует бюджет. Модель не отправляет сообщения через произвольные файлы или shell как обход платформенной доставки.

Доставка: accepted → queued → delivered_to_context → acknowledged либо rejected/expired/dead_letter. accepted означает запись в надёжное хранилище; delivered_to_context — успешную передачу во вход конкретного turn. acknowledged требует явного прикладного подтверждения, если оно предусмотрено контрактом.

Получатель не обязан отвечать на каждое сообщение. Инструкция и тип сообщения задают необходимость ответа. Антипетля: ограничение hops, maxReplies, duplicate body detection в пределах диалога, time budget и эскалация при отсутствии прогресса.

### FR-10. MCP

Каталог подключений содержит понятные рецепты, свои серверы, версию, издателя, способ авторизации, обязательные поля и диагностические шаги.

Каждая карточка имеет переключатель, статус здоровья и область доступа. Первое включение ненастроенного подключения открывает мастер; переключатель не становится «подключён», пока проверка не завершилась.

Отдельно задаются tools allowlist, ресурсы/папки/namespace, чтение/запись и required/optional для роли или задачи. Сбой optional MCP даёт предупреждение; сбой required блокирует запуск или зависимую подзадачу.

MCP не заменяет установку базы, загрузку документов, индексацию или выдачу прав. Эти операции показаны отдельными шагами.

### FR-11. Знания и память

Источники: разрешённые локальные каталоги, документы, подключённые БД, удалённое файловое/объектное хранилище через MCP. Источник имеет владельца, namespace, видимость, retention и политику обновления.

Конвейер: discover → fetch → parse → index → ready; для некоторых MCP доступ возможен on-demand без локального индекса. Неопознанный формат имеет состояние unsupported, а не пустой успешный индекс.

Каждое утверждение в графе знаний: текст/тип, source URI, source version/hash, автор, время, namespace, статус проверки, связи supports/contradicts/derived_from. Вывод агента хранится как утверждение с происхождением; не становится подтверждённым фактом автоматически.

Граф знаний и агентный граф разделены на уровне типов и хранения. Объединённый вид показывает связь «агент прочитал источник»/«агент создал утверждение».

Без общей памяти агент использует собственный контекст и явно разрешённые источники. Отключение памяти прекращает новые обращения; ранее переданные сведения остаются в истории. Для исключения такого контекста нужна новая сессия, UI это объясняет.

### FR-12. Наблюдаемость

Граф показывает состояние runtime, задачи, очередь, доставку сообщений и обращения к хранилищам. Выбор узла открывает роль, текущую задачу, события, диалог, результаты, права и диагностику.

Показываются доступные публичные планы/краткие сводки исполнителя, вызовы инструментов и результаты. Полный скрытый ход рассуждений не обещается и не имитируется. Если провайдер не отдаёт прогресс, UI показывает «Выполняется; подробные события недоступны».

Есть live/replay, фильтры времени и типов, причинные связи, поиск по ID/роли/имени, список агентов как доступная альтернатива графу. Replay не запускает инструменты повторно.

### FR-13. Управление работой

- Пауза выдачи: новые задания не стартуют, активные turn доходят до границы.
- Прервать агента: отменить текущий attempt; артефакты сохранить с пометкой partial.
- Остановить run: закрыть вход задач и каскадно отменить его потомков.
- Аварийная остановка workspace: запрет новых lease и сетевых/MCP операций, завершение принадлежащих приложению процессов.
- Повтор: новая попытка; автоматический повтор разрешён только при классифицированном transient failure и известной безопасности внешних эффектов.

UI показывает различие «команда остановки принята», «процесс завершён» и «внешняя операция уже могла завершиться».

### FR-14. Результаты

Артефакт: ID, тип, версия, hash, автор/attempt, время, путь/объектный URI, статус приёмки. Поддержать Markdown, текст, JSON, изображения, прикреплённые файлы и diff кода; прочие типы можно скачать.

Общий output собирается в отдельное место. Несколько агентов не пишут одновременно в один файл. Для кода — отдельные worktree/копии и этап интеграции с проверкой конфликтов.

У каждой принятой задачи есть финальное сообщение с кратким результатом, списком артефактов, ограничениями и невыполненными критериями.

### FR-15. Ресурсы и расход

Показывать созданные, queued, running, waiting, stopped, failed; CPU/RAM исполнителей; задержку очереди; throughput; ошибки; tool latency; provider usage, если есть.

API-стоимость рассчитывается только по известным usage и выбранной версии прайс-листа, с пометкой «оценка». Неизвестный расход — неизвестен, не 0. Вход через ChatGPT показывает доступные provider limits или «Лимит не предоставлен»; денежная стоимость каждого turn по подписке не выдумывается.

Один набор credentials имеет общий ограничитель. Создание новых экземпляров не обходится как создание новых квот.

### FR-16. Импорт, экспорт и история

Экспорт архитектуры человекочитаем и проходит JSON Schema. Нужны migrationVersion, schemaVersion, roleVersions и connection placeholders. Секреты исключаются; локальные абсолютные пути требуют remap при импорте.

Изменения конфигурации фиксируются с author, timestamp, reason, previousRevision. Undo/redo для черновика; изменение уже запущенной истории недопустимо.

### FR-17. Будущие исполнители

Runtime registry обнаруживает наличие Codex, Claude Code и API-конфигураций. В первом выпуске реально доступен только Codex; остальные помечаются «Запланировано» без рабочего переключателя.

Будущий API-агент сохраняет семантику отдельного экземпляра/контекста; его процессная модель будет описана в отдельной спецификации адаптера. Условие «1000 Codex = 1000 Codex CLI» не размывается последующим API-пулом.

### FR-18. Эксплуатация и доступ

Локально — OS-права, секретное хранилище, заблокированное внешнее управление по умолчанию. Командная версия — роли viewer/operator/editor/admin, разграничение workspace, отдельные identities удалённых worker.

Нужны миграции БД, резервное копирование, восстановление, экспорт диагностического пакета с редактированием секретов, подписанные обновления и откат совместимой версии.

## 6. Масштаб и ресурсы

| Масштаб | Продуктовое поведение | Условие доказанной поддержки |
|---|---|---|
| N=1, C=1 | Один узел, один Codex, прямой чат | Реальная end-to-end проверка |
| N=10, C=10 | 10 отдельных процессов и историй | Параллельный smoke + отмена + проверка изоляции |
| N=1000, C=10 | Все 1000 экземпляров существуют; 10 исполняются, остальные ждут | Надёжная очередь и UI 1000 узлов |
| N=1000, C=1000 | 1000 выделенных Codex, распределяемых по worker | Реальные разрешённые ресурсы и квоты, длительный нагрузочный прогон |
| N=5000+ | Вложенные холоны, агрегация графа, lazy history | Отдельный сертифицированный профиль масштаба |

Целевой размер редактируемой конфигурации первой модели — 5000 экземпляров и 25000 разрешённых рёбер. Это лимит продукта для первого набора нагрузочных сценариев, а не теоретический предел.

Требуемая RAM = overhead приложения + C × измеренная p95 RAM Codex + MCP overhead + индекс/кэш + резерв. До измерения конкретного runtime численные обещания памяти не даются.

Запрос C выше доступной вместимости не приводит к зависанию: admission показывает ограничения и даёт выбрать явный лимит, очередь или подключение worker. Для задания «требуются все 1000 одновременно» запуск блокируется до наличия 1000 слотов; нельзя молча запускать только 10.

Полный граф all-to-all запрещён как автоматический default: для 1000 узлов он создаёт 999000 направленных связей. Используются holon gateways, topic subscriptions с ACL и явные рёбра.

## 7. Что входит в первый production-выпуск

Локальные рабочие области, роли и версии, независимые экземпляры, ручные холоны, отсутствие/наличие координатора, optional memory, Codex exec adapter, прямые и глобальные задачи, надёжная очередь, платформенные сообщения, MCP master для файлов/Neo4j/custom, граф и список, артефакты, cancel/recovery, аудит и бюджеты.

Для запуска первая production-ступень должна доказать 1–10 одновременных Codex на определённом тестовом стенде. Создание 1000+ экземпляров в этом же выпуске возможно с очередью и честным отображением фактического C.

Полная цель продукта включает удалённых worker и 1000+ одновременно работающих Codex. Это обязательный следующий выпуск, а не замена требования пользовательским демо.

## 8. Что не обещается исходной спецификацией

Неограниченная подписочная квота; вывод скрытых рассуждений; автоматическая истинность графа знаний; exactly-once для любых внешних инструментов; произвольная безопасная установка неизвестного MCP; одинаковая семантика pause у всех CLI; автоматическая миграция сессии между провайдерами.

Каждый из этих случаев имеет конкретное поведение ошибки или ограниченной возможности, описанное в последующих документах.
