# ADR-017 — разрешение для конкретного следующего turn

Статус: принято для следующих срезов D10. Основание: FR-11 и протокол exec approval из раздела 03 §8.

Разрешение нельзя переносить с истёкшего lease на произвольную следующую попытку. Поэтому при запросе операции служба заранее выделяет **идентификатор одной следующей попытки** этого агента. Это резервирование номера, без процесса и без занимаемого process slot. Исходный turn имеет `originEpoch`; exact operation указывает отдельный будущий `epoch`. Оба входят в fingerprint. Reservation, запрос разрешения и его receipt сохраняются одной транзакцией.

После успешного reap исходной попытки задача входит в waiting_user. Пока решение не получено, другие агенты используют свободный слот, а другие задачи **этого же экземпляра** не обгоняют ожидающую операцию. Это сохраняет порядок fencing для отдельного агента и последовательность его рабочего контекста. После решения (включая отказ) та же задача продолжает ту же Codex-сессию с заранее выделенным epoch. Остальные экземпляры могут тем временем получать более высокие номера; проверка lease всегда учитывает task/agent и точное текущее значение, а не один глобальный maximum.

Продолжение получает approval ID. Отдельный инструмент исполнения проверяет действующее решение, agent/task/run/epoch, срок, live∩pinned binding, namespace, connection revision и resource scope. Аргументы читаются из замороженной операции на стороне службы; модель не заменяет их после решения. Перед контактом с MCP ledger атомарно переходит approved → executing. Повтор не отправляет внешний эффект второй раз. Это соответствует исходному требованию: operation_pending быстро завершает первый turn, а внешний вызов происходит в новой одобренной попытке.

Отмена, crash/reconcile или обычное завершение без перехода к ожиданию уничтожают reservation; выделенный номер больше не используется. Позднее решение не воскрешает задачу. После начала внешнего вызова потеря ответа/связи означает unknown, а не разрешение на повтор. Неизвестный исход требует отдельной сверки владельцем. Одобрение показанного запроса не является политикой auto-approve для будущих запросов.

В D10w доступны request/status/execute, atomic Engine reservation/receipt, park/resume и owner HTTP/UI. Request имеет срок 15 минут без продления при повторе. Execute принимает только approvalId. После consume reply/error/cancellation не разрешают повтор: успешный MCP result сохраняется вместе с succeeded, а isError тоже считается unknown, поскольку сервер мог частично изменить ресурс. Новый запрос или message wait в execution turn запрещены до разрешённого исхода предыдущей операции. Отзыв attempt grant распространяется на уже выполняющиеся вызовы; transport не переинициализирует истёкшую HTTP-сессию для повторной отправки. STDIO/HTTP fixtures проверены, actual Codex write остаётся самостоятельным gate. Existing read-only source tool остаётся read-only.
